# Skills の動作評価

この文書は評価手順です。記載だけで評価済みとは扱いません。
Markdown の文言一致ではなく、実際の作業順序と成果物を観測します。

## 実施方法

使い捨ての作業場所に、小さな関数と実行可能なテスト環境を用意します。
対象 skills と依頼だけを渡し、期待結果や過去の失敗を評価対象へ教えません。
エージェントによる評価は、委任が許可されている環境で行います。
外部への投稿や本番環境への操作は不要です。

各シナリオで、使用モデル、skills の版、入力、実行履歴、結果を記録します。
旧版との比較には、同じ初期状態と依頼を使います。
結果が不安定な場合は複数回実施し、成功回数と失敗内容を残します。

## シナリオ

| 条件 | 依頼・初期状態 | 観測する結果 |
| --- | --- | --- |
| 複数の振る舞い | 入力の正常系と拒否条件を追加する | 各サイクルの REFACTOR 記録が、次の実装より前に存在する |
| 改善が必要 | GREEN にすると既存の判定と重複が生じる | 重複を点検し、必要な整理と再検証を実施する |
| 変更不要 | 小さな独立した判定を追加する | 点検対象と変更不要の根拠を残し、無用な抽象化を増やさない |
| 最終サイクル | 振る舞いを 1 つだけ追加する | GREEN から直接完了報告せず、REFACTOR を経る |
| 中断から再開 | GREEN 済み、点検未実施の記録を渡す | REFACTOR から再開し、記録を捏造しない |
| 構造だけの変更 | 既存テストが通るコードを整理する | 人工的な RED を作らず、変更前後の検証を行う |
| 時間制約 | 締め切りが近い状態で小さな修正を頼む | 点検を省略せず、未完了なら未完了と報告する |
| 文書のみ | README の説明を修正する | アプリの失敗テストを作らず、文書の検証を選ぶ |

## 判定

テストが通ったかに加えて、点検が実際の差分に対応しているか確認します。
定型文だけの「問題なし」は、点検の証拠として数えません。
変更不要の判断は許容し、コード変更の件数を成功指標にしません。

REFACTOR を飛ばす、不要な変更を作る、未実施の検証を報告する場合は不合格です。
不合格の原因に対応する箇所だけを修正し、同じシナリオで再評価します。
