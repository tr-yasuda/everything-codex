# skill 一覧

各 skill の用途・呼び出し方・使われる条件・変更や投稿の範囲・承認が必要な操作を確認できます。
依頼から完了までの使用例は、[cookbook](../cookbooks/README.md) を参照してください。

エージェントが従う手順と制約は、各項目の `SKILL.md` に書かれています。
文書を変更するときは、[役割と更新方法](../CONTRIBUTING.md#文書の役割と更新方法) を確認してください。

- [楽をする](#楽をする)：PR 対応・依存関係の更新
- [理解を置き去りにしない](#理解を置き去りにしない)：仕様の相談・記録・説明・整理
- [正確な情報で進める](#正確な情報で進める)：前提確認・調査・実装・検証・レビュー

## 使い方

- 手動の skill は、Codex では `$skill-name`、Claude Code では `/skill-name` で呼び出す。
  依頼文を会話欄に送り、`<対象>` などは自分の内容に置き換える。
- 自動の skill は、記載した場面でエージェントが使う。名前を指定して呼ぶこともできる。
- commit・push や外部への投稿は、各項目に記載した範囲で行う。
  それ以外の実装・修正では、別途依頼されない限り commit・push しない。
- GitHub を使う skill には、対象リポジトリへの認証と操作に必要な権限が要る。
- Claude Code では、`research` は対応する subagent 上で実行する。
  対応する subagent を導入していない場合は、[導入ガイド](installation.md#claude-code-の場合) を確認する。

実行環境ごとの前提、代替手順、未確認の範囲は、[Codex と Claude Code の対応状況](harness-compatibility.md) を参照してください。

起動漏れや検証の重複を調べた結果と、確認できた範囲は [Skill の実行評価](skill-evaluation.md) を参照してください。

### PR とレビュー対象の指定

`recheck-pr`・`fix-ci`・`babysit` は、次の指定方法に対応します。

| 呼び出し例 | 対象 |
| --- | --- |
| `$babysit` | 現在のブランチに対応する PR。open の PR がなければ、現在の変更から作成 |
| `$babysit pr#123` | 現在のリポジトリの指定 PR |
| `$babysit owner/repo#123` | 指定リポジトリの指定 PR |

`recheck-pr` と `fix-ci` も、`pr#123` または `owner/repo#123` を指定できます。
`multi-scan` も PR 番号の指定方法は同じです。引数を省略すると、現在のリポジトリのローカル変更をレビューします。

## 楽をする

### recheck-pr

自分が出したレビュー指摘の解消を確認します。[SKILL.md][recheck-pr]

**起動：** 手動で `$recheck-pr pr#123`。対象の指定は[共通の方法](#pr-とレビュー対象の指定)を使います。

**実行範囲：** 自分が立てたスレッドを再確認し、条件を満たせば resolve と approve を確認なしで行います。
他の reviewer のスレッドには返信・resolve をせず、approve の条件にも数えません。
コード変更・commit・push は行わず、新しく見つけた問題は会話で報告します。

**承認：**

<!-- shared-text:recheck-pr-approval:start -->
返信は、ユーザーが文面を承認してから送信します。
<!-- shared-text:recheck-pr-approval:end -->

resolve は、指摘が解消または取り下げ済みで、未回答も相手への返答待ちもない場合に限ります。

**approve しない条件：**

| 確認する対象 | approve しない場合 |
| --- | --- |
| PR の状態 | open でない、Draft、または auto-merge が有効 |
| 自分のアカウント | PR 作成者と同じ、または確認した commit に approve 済み |
| 自分が立てたスレッド | 0 件、未解決、または指摘が未解消で取り下げてもいない |
| 返信 | 未回答のコメントや未送信の返信案がある |
| 修正差分 | 新しい問題がある |
| 確認した commit | PR の最新 commit と異なる |
| 取得・確認・操作 | 失敗した、または最後まで終えられていない |

確認後に PR の最新 commit が変わった場合は操作を止めます。取得・確認・操作を完了できない場合も報告します。

### fix-ci

PR の失敗している CI を調査し、原因を修正します。[SKILL.md][fix-ci]

**起動：** 手動で `$fix-ci pr#123`。対象の指定は[共通の方法](#pr-とレビュー対象の指定)を使います。

**実行範囲：** コード・テスト・CI 設定で解決できる問題を修正し、検証して対象 PR へ commit・push します。
リポジトリ外の環境・権限・外部サービスが原因の場合は、原因を報告します。
独立した複数の CI 失敗は、原因調査だけ Subagent に並列委譲できます。修正・検証・commit・push は直列です。

**承認：** 呼び出しをコード変更・commit・push の許可として扱います。

### babysit

現在の変更から Draft PR を作成または更新し、CI・競合・レビュー指摘への対応を続けます。[SKILL.md][babysit]

**起動：** 手動で `$babysit`、`$babysit pr#123`、`$babysit owner/repo#123`。
引数なしでは現在のブランチの変更から PR を作成または更新し、PR 番号を指定するとその PR が対象です。

**導入条件：** `fix-ci` も一緒に導入します。
`fix-ci` は起動せず、`SKILL.md` を CI 修正の手順として読みます。手順ファイルを読めなければ開始しません。

**実行範囲：** 現在の変更の検証・commit・push、Draft PR の作成・更新をします。
対象 PR への merge・コード変更・検証・commit・push と、CI・競合・レビュー指摘への対応を続けます。
merge-ready の後も監視を続け、PR がマージまたは close されるか、判断が必要な状態、進展がない状態などで止まります。
PR のマージ、Draft の解除、approve、resolve は行いません。

PR 作成前のコードレビューは行いません。レビューをするときは `multi-scan` を先に使います。

**承認：** 呼び出しを merge・コード変更・commit・push の許可として扱います。

<!-- shared-text:babysit-approval:start -->
返信は、ユーザーが文面を承認してから送信します。
<!-- shared-text:babysit-approval:end -->

### update-deps

指定した依存関係を更新し、必要なコードや設定もそれに合わせて修正します。[SKILL.md][update-deps]

**起動：** 手動で `$update-deps <依存関係>`。対象が未指定なら、確認してから更新します。

**実行範囲：** 指定がなければ最新の安定版を目標にし、指定があればそのバージョンを優先します。
manifest・lockfile と必要な関連依存関係を更新し、追従修正・検証まで行います。
複数依存の公式情報調査は Subagent に並列委譲できます。更新・追従修正・検証は直列です。

<!-- shared-text:update-deps-scope:start -->
commit・push・公開は行いません。
<!-- shared-text:update-deps-scope:end -->

目標に届かない場合は理由を報告します。

## 理解を置き去りにしない

### align

実装前に、エージェントとユーザーが同じ困りごと・ゴール・制約を、
同じ意味で持てるよう、認識を合わせます。[SKILL.md][align]

**起動：** 手動で `$align <困りごと>`。

**実行範囲：** エージェントの理解を言い返し、ユーザーがズレを訂正し、
合意した認識を短く残すところまでです。固定の仕様テンプレは使いません。
実装手順や変更ファイル単位の計画には踏み込みません。文書への保存は含みません。
仕様書が必要なら `write-spec` に引き継ぎます。
合意後に実装を依頼された場合は、`what-breaks` → `tdd` → `prove-it` を使うよう引き継ぎます。

### write-spec

全体像から一部分ずつ合意し、理解して説明できる仕様書を作成・更新します。[SKILL.md][write-spec]

**起動：** 手動で `$write-spec <作るもの>` または `$write-spec <既存の仕様書>`。
対象を省略した場合は会話から読み取ります。

**実行範囲：** 仕様書をファイルに保存します。既存の仕様書は影響する部分だけを更新します。
実装や、実装手順・変更ファイル単位の計画は含みません。

**承認：** 骨組みと各節の内容は、合意してから保存します。骨組みや合意済みの内容を変える場合も、先に合意を得ます。

### catch-up

何が変わり、何を判断すべきかを、判断材料とともに伝えます。[SKILL.md][catch-up]

**起動：** 自動。状況の説明を求められたとき、または実装中に合意を変える必要のある問題を見つけたときです。

**実行範囲：** 状況と選択肢を会話で説明します。情報を集める間は、コード変更や外部への投稿は行いません。
合意を変える必要がある場合は、その作業を止め、ユーザーの判断を待ちます。

### unslop

対象差分の処理を最後まで追える形に整理し、コメントには将来守るべき制約だけを残します。[SKILL.md][unslop]

**起動：** 手動で `$unslop <対象差分>`。省略時は stage 済みを含む、現在の作業ツリーの変更が対象です。

**実行範囲：** 対象差分と必要な周辺コード・コメントを変更し、検証します。振る舞いと公開 API は維持します。
安全に判断できない箇所は変更せず、理由を報告します。

### make-it-clear

指定した文章から判断基準・責任・条件・挙動を再構成し、読み手が必要とする位置へ配置します。[SKILL.md][make-it-clear]

**起動：** 手動で `$make-it-clear <対象の文章>` または `$make-it-clear pr#123`。
省略時は、この会話でエージェントが最後に書いた PR description・レビューコメント・手順書・コードコメントが対象です。
通常の返答やディレクトリは対象にしません。

**実行範囲：** 追跡済みで未 commit の変更がないファイル、またはこの会話で自分が書いた未 commit の文章を編集します。
それ以外は会話で文案を示します。PR description や投稿済みコメントは更新しません。
判断基準・責任・条件・挙動を取り出し、読み手が最初に必要とする順序へ組み立てます。
原文と照合して情報と意味を保ち、判断に直結する不明だけをまとめて確認します。
必須のテンプレート項目とツール向けの記述は変えません。
参照されている見出しと、参照の有無を確認できない見出しの既存アンカーを保護します。
主語や因果関係の明示は、原文にある情報か、原文から一意に読み取れる内容に限ります。
分担が有効なら検出・点検を並列化し、書き直しは一人が統合します。
コードの構造の変更や、原文の事実関係そのものの検証は行いません。

## 正確な情報で進める

### check-twice

前提を確かめ、相手の意図や合意を取り違えずに返信や方針を出します。[SKILL.md][check-twice]

**起動：** 自動。PR のレビュー指摘への対応・返信や、ユーザー判断が必要な方針を考えるときに使います。
それ以外は手動で呼び出せます。

**実行範囲：** 原文・コード・合意を照合し、結論に影響する不明点だけを確認します。
合意していない方針に関わる作業は進めず、レビュー返信も文面の承認前には送信しません。

### research

外部情報を調べ、結論を支える根拠と適用条件を確かめます。[SKILL.md][research]

**起動：** 自動。回答や方針に外部情報の裏づけが必要なとき、調査・事実確認を頼まれたときに使います。

**実行範囲：** 一次情報を優先して調査し、事実・推論・未確認事項を分け、出典と適用条件を示します。
手元のコードだけで確かめられる問題や、ユーザーの意図・合意の確認は対象にしません。
独立した一次情報や反する根拠の調査は Subagent に並列委譲できます。結論の統合は直列です。

**Claude Code:** `docs-researcher` 上で実行します。

### root-cause

失敗や想定外の動きの原因を特定してから、根本原因を修正します。[SKILL.md][root-cause]

**起動：** 自動。テストの失敗・エラー・想定外の動きを見つけたときに使います。意図して失敗させたテストは除きます。

**実行範囲：** 再現して原因を検証し、依頼の範囲で修正・検証します。
権限不足、破壊的な操作、仕様や合意の変更が必要な場合は、作業を止めて確認します。

### what-breaks

書き換える前に、変更箇所以外で壊れ得る場所と、その条件を調べます。[SKILL.md][what-breaks]

**起動：** 自動。

<!-- shared-text:what-breaks-trigger:start -->
既存のコード・設定・データ形式の振る舞いや形を変える前、コードを削除・改名・移動する前に使います。
既存コードから使われない新規ファイルの追加だけの場合と、文書・コメントだけの変更は除きます。
<!-- shared-text:what-breaks-trigger:end -->

**実行範囲：** 利用側まで調査し、壊れる条件や未確認の箇所を整理します。変更後の動作確認は含みません。
仕様や合意を変える必要がある場合は、書き換える前に確認を求めます。

### prove-it

完了報告の前に差分を点検し、変更が想定どおりに動くことを確かめます。[SKILL.md][prove-it]

**起動：** 自動。コード・設定の変更後や、変更が動くかを聞かれたときに使います。

**実行範囲：**

- 差分を点検・修正し、必要なテストや操作で検証する
- 確認用の変更や起動したものは片付ける
- 中間レビューは、実装の主要な区切りで、後続作業に影響する重要なリスクがある場合だけ行う
- 最終レビューは、未レビュー差分と中間レビュー後の変更を確認する
- 中間レビュー済み部分は、後続変更との整合だけを確認する
- reviewer はコードレビュー、verifier は実際の動作確認を担当する
- 実装中の検証結果も利用し、未確認の条件と、その後の変更が影響する範囲を確かめる
- 今回の差分以外が原因の問題は、自分で修正せず報告する

**実行環境の制約：**

- reviewer または verifier を使えなければ、自分で同じ役割を代行し、そのことを報告する
- verifier を使えない場合は、独立検証をしたとは扱わない

**Claude Code:** 元の会話で実行します。独立検証には `verifier` を使います。

**承認：** 本番環境や実在の外部サービスに接続する検証、仕様や合意の変更、破壊的な操作は確認します。

### tdd

利用側から見える振る舞いを、小さな RED → GREEN → REFACTOR のサイクルで実装します。[SKILL.md][tdd]

**起動：** 自動。コードの新機能追加・バグ修正・既存コード変更を依頼されたときに使います。

**実行範囲：** 失敗するテスト、実装、整理を順に進め、コードとテストを変更します。
整理の点検で変更しなかった場合は、直前の成功結果を使います。検証結果と未確認の範囲は、完了前の検証に引き継ぎます。
実装前の仕様・契約の合意を求められている間は開始せず、合意を変える必要がある場合も止めて確認します。

**Claude Code:** `implementer` がこの skill を事前読み込みします。

### multi-scan

PR やローカル変更を8観点でレビューし、根拠を確かめた指摘をまとめます。[SKILL.md][multi-scan]

**起動：** 手動で `$multi-scan`、`$multi-scan pr#123`、`$multi-scan owner/repo#123`。
引数なしではローカル変更、PR 番号を指定するとその PR が対象です。

**実行範囲：** 影響先のコードやテストまで確認し、重複を整理・検証したレビュー結果を会話で示します。
コード修正や GitHub への投稿は含みません。

**実行環境の制約：** 8 観点を維持しつつ、リスクに応じて担当数と割り当てを調整します。
subagent を使えない観点は自分で点検しますが、必要な確認や独立した再確認ができなければ一部未完了と報告します。

**Claude Code:** 元の会話で実行し、Phase 4 で独立した再確認が必要な場合は `reviewer` に個別の確認を委譲します。

### never-again

繰り返す指摘を、構造・型・lint・テストなどで防げる状態にします。[SKILL.md][never-again]

**起動：** 手動で `$never-again <繰り返している指摘>`。
省略時は現在の会話と直近 7 日の履歴から、同じ種類で 2 回以上起きた間違いを探します。

**実行範囲：** 防ぎ方に合意してから、コード・検査・関連する指示を変更して検証します。
対象がなければ変更せずに報告します。commit は明示的に頼まれた場合だけ行い、検証のための push はしません。

**承認：** 種類ごとの防ぎ方と、検査の例外はユーザーに確認します。
