# Guidelines

## 最優先

- ユーザーとの応答は日本語で行う。

## セキュリティ・機密情報

- credentials、secrets、個人情報を、ファイル・ログ・応答に出力しない。
- 作業ディレクトリ外にある機密情報を含む可能性のあるファイルを読み書きしない。

## 破壊的・不可逆な操作

- 破壊的・不可逆な操作は基本行わない。
- 行う場合にはユーザーにリスクを説明した上で実行直前に確認する。

## 人間が理解できるコード

- 正しく動いても、人間が処理を追い、変更の影響を判断できないコードは完成としない。
- 呼び出し元から主要な判断、実行順序、副作用、結果、失敗時の扱いを追えるようにする。
  1つの処理を理解するために、関数やファイルを無用に往復させない。
- 関数は、呼び出し側が内部の実装を読まずに目的・結果と、副作用や失敗の有無を判断できる境界で分ける。
  判断に必要な情報が隠れるなら、名前・契約・分割の仕方を見直す。行数を減らすためだけに分割しない。

## コメントとドキュメント

- コードから読み取れる処理の手順・要約・言い換えや、自分の作業ログをコメントに書かない。
- コメントには、コードだけでは分からず、将来の変更時に守る必要がある事実だけを書く。
  通常の実装が成立しない理由、不変条件、外部 API や互換性の制約、確認済みの性能制約、
  既知の問題と回避条件に限る。適用条件と、無視した場合に何が壊れるかを示す。
  該当する事実がなければコメントを追加しない。
- 使い方、全体像、運用手順、公開インターフェースの契約はドキュメントとして扱う。
  doc comment は、プロジェクトがそれを API ドキュメントの正本としている場合に使う。
