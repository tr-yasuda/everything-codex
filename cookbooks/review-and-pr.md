# 手元の変更に問題がないか確認して、レビューに出したい

自分が送る依頼: `$code-review` → 必要な修正を依頼 → `$create-pr`。

自動で使われる skill: コードを修正する場合は `tdd`、変更後の確認には `verify-change`。

検索欄が空なら検索しない、という変更を手元で実装しました。
想定していない問題を確認し、チームにレビューしてもらう Draft PR を作ります。
PR の作成には、GitHub への認証と対象リポジトリへの書き込み権限が必要です。

## 1. 手元の変更をレビューする

```text
$code-review
検索欄が空なら検索しないように変更しました。
現在のローカル変更をレビューしてください。
```

引数なしでは、現在のリポジトリのローカル変更をレビューします。
レビューでは指摘と根拠、推奨する対応が返ります。この呼び出しだけで修正や commit・push は行いません。

返ってきた内容で、どの条件で問題が起きるか、影響は何か、対応が必要かを確認します。
分からない指摘は、その点の説明を頼みます。
指摘がなければ、修正の依頼を省いて PR の作成へ進めます。

## 2. 必要な修正と検証を頼む

例えば、スペースだけを入力すると検索が走る、という指摘があったとします。
スペースだけの場合も検索しないのが意図した仕様なら、その修正を頼みます。

```text
スペースだけの入力も、空の入力と同じく検索しないのが意図した仕様です。
レビューで指摘された、この問題を修正してください。
再発を防ぐテストと、関連する検証までお願いします。commit・push はまだ不要です。
```

修正内容と検証結果を読み、問題が解消されたことを確認します。
修正と検証を頼めば、`tdd` や `verify-change` を別に呼ぶ必要はありません。
新たな懸念があれば、その点を説明して、追加の確認やレビューを頼みます。

## 3. Draft PR を作成する

共有する差分と検証結果を確認できたら、次を送ります。

```text
$create-pr
```

この呼び出しで、必要な検証の確認、commit、push、Draft PR の作成まで進みます。
同じブランチに既存の PR がある場合は、その PR を更新します。
無関係な変更は commit に含めません。

PR のリンクを開き、差分、変更理由、検証結果が意図した内容になっているか確認します。
Draft PR は、レビューの準備ができるまで下書きとして扱う PR です。

## 完了の目安

対象の変更が push され、意図した差分と説明を持つ Draft PR が作成または更新されていることです。
レビューだけが目的なら、指摘と対応方針を確認した段階で終えられます。
PR に指摘や CI の失敗が出たら、[PR の問題に対応する](maintain-pr.md) を参照してください。
