# 手元の変更に問題がないか確認して、レビューに出したい

自分が送る依頼: `$multi-scan` → 必要な修正を依頼 → `$create-pr`。

自動で使われる skill: コードを修正する場合は `what-breaks` と `tdd`、変更後の確認には `prove-it`。

検索欄が空なら検索しない、という変更を手元で実装しました。
想定していない問題を確認し、チームにレビューしてもらう Draft PR を作ります。
PR の作成には、GitHub への認証と対象リポジトリへの書き込み権限が必要です。

## 1. 手元の変更をレビューする

```text
$multi-scan
検索欄が空なら検索しないように変更しました。
現在のローカル変更をレビューしてください。
```

引数なしでは、現在のリポジトリのローカル変更をレビューします。
コードとテストに加えて、差分内の文書とコメントが管理・保守に使えるかも確認します。
レビューでは指摘と根拠、推奨する対応が返ります。この呼び出しだけで修正や commit・push は行いません。

返ってきた内容で、どの条件で問題が起きるか、影響は何か、対応が必要かを確認します。
分からない指摘は、その点の説明を頼みます。
指摘がなく、レビューが一部未完了とも報告されていなければ、修正の依頼を省いて PR の作成へ進めます。
一部未完了なら、代わりに点検した観点と残る確認を読み、必要なレビューを実施できる環境で補います。

## 2. 必要な修正と検証を頼む

例えば、スペースだけを入力すると検索が走る、という指摘があったとします。
スペースだけの場合も検索しないのが意図した仕様なら、その修正を頼みます。

```text
スペースだけの入力も、空の入力と同じく検索しないのが意図した仕様です。
レビューで指摘された、この問題を修正してください。
再発を防ぐテストと、関連する検証までお願いします。commit・push はまだ不要です。
```

修正内容と検証結果を読み、問題が解消されたことを確認します。
修正と検証を頼めば、`what-breaks`、`tdd`、`prove-it` を別に呼ぶ必要はありません。
新たな懸念があれば、その点を説明して、追加の確認やレビューを頼みます。

## 3. Draft PR を作成する

共有する差分と検証結果を確認できたら、次を送ります。

```text
$create-pr
```

この呼び出しで、必要な検証、commit、push、Draft PR の作成まで進みます。
結果のない検証は、その場で実行します。
commit する内容を検証します。commit しない変更が作業ツリーにあれば、それを除いた別の作業場所で検証します。
検証のあとで commit する内容が変わっていたら、push をせずに、変わったファイルを報告して止まります。
commit したあとに分かった場合、その commit は手元に残ります。
検証が失敗したら、commit・push・PR の作成と更新をせずに、失敗の内容を報告して止まります。
`$create-pr` は失敗を直さないので、修正と再検証を頼んでから、もう一度呼びます。
環境の制約で実行できなかった検証は、その範囲と理由を PR の本文に書き、チェック欄を空のままにします。
commit message と PR の本文は、公開前に差分と検証結果に照らして直されます。
同じブランチに open の PR がある場合は、その PR を更新します。
ない場合は、ブランチ名を変更内容を表す名前へ、確認なしで変えてから push します。
無関係な変更は commit に含めません。

PR のリンクを開き、差分、変更理由、検証結果が意図した内容になっているか確認します。
Draft PR は、レビューの準備ができるまで下書きとして扱う PR です。

## 完了の目安

対象の変更が push され、意図した差分と説明を持つ Draft PR が作成または更新されていることです。
レビューだけが目的なら、指摘と対応方針を確認した段階で終えられます。
PR に指摘や CI の失敗が出たら、[PR の問題に対応する](maintain-pr.md) を参照してください。
