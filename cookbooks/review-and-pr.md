# 手元の変更をレビューして、PR のマージまで任せたい

自分が送る依頼: `$multi-scan` → 必要な修正を依頼 → `$babysit`。

自動で使われる skill: コードを修正する場合は `what-breaks` と `tdd`、変更後の確認には `prove-it`。

検索欄が空なら検索しない、という変更を手元で実装しました。
想定していない問題を確認し、チームにレビューしてもらう Draft PR を作って、マージまで対応を任せます。
PR の作成には、GitHub への認証と対象リポジトリへの書き込み権限が必要です。

## 1. 手元の変更をレビューする

```text
$multi-scan
検索欄が空なら検索しないように変更しました。
現在のローカル変更をレビューしてください。
```

引数なしでは、現在のリポジトリのローカル変更をレビューします。
コードとテストに加えて、差分内の文書とコメントが管理・保守に使えるかも確認します。
レビューでは指摘と根拠、推奨する対応が返ります。この呼び出しだけで修正や commit・push は行いません。

返ってきた内容で、どの条件で問題が起きるか、影響は何か、対応が必要かを確認します。
分からない指摘は、その点の説明を頼みます。
指摘がなく、レビューが一部未完了とも報告されていなければ、修正の依頼を省いて PR の作成へ進めます。
一部未完了なら、代わりに点検した観点と残る確認を読み、必要なレビューを実施できる環境で補います。

## 2. 必要な修正と検証を頼む

例えば、スペースだけを入力すると検索が走る、という指摘があったとします。
スペースだけの場合も検索しないのが意図した仕様なら、その修正を頼みます。

```text
スペースだけの入力も、空の入力と同じく検索しないのが意図した仕様です。
レビューで指摘された、この問題を修正してください。
再発を防ぐテストと、関連する検証までお願いします。commit・push はまだ不要です。
```

修正内容と検証結果を読み、問題が解消したことを確認します。
修正と検証を頼めば、`what-breaks`、`tdd`、`prove-it` を別に呼ぶ必要はありません。
新たな懸念があれば、その点を説明して、追加の確認やレビューを頼みます。

## 3. Draft PR の作成と監視を任せる

共有する差分と検証結果を確認できたら、次を送ります。

```text
$babysit
```

現在の変更を検証し、commit・push して Draft PR を作成または更新します。
続いて CI・merge conflict・未解決のレビュー指摘を確認し、必要な修正を commit・push します。
CI の結果、レビュー、マージ可否を GitHub から取得し直し、PR がマージされるまで監視します。

PR を作成するときの検証に失敗した場合、`$babysit` は commit・push・PR の作成をせずに止まります。
失敗の内容を確認し、修正と再検証を頼んでから、もう一度呼びます。
検証の後に commit する内容が変わった場合も、push せずに変わったファイルを報告して止まります。

レビュー指摘を修正した場合は、返信案が提示されます。
返信は、文面を承認してから送信されます。承認後に監視が再開します。

## 4. 結果を確認する

PR がマージされると `$babysit` は止まり、対象 PR と確認した HEAD、行った対応、検証結果を報告します。
PR がマージされずに close された場合や、仕様判断、権限、外部サービスの対応が必要な場合も止まります。
止まった理由と残っている問題を読み、必要な判断をします。

## 完了の目安

対象の変更が push され、意図した差分と説明を持つ Draft PR が作成または更新されていることです。
その後は、PR がマージされるか、残っている問題と必要な判断を把握できていることです。
