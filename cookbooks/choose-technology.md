# 外部技術を調べて採用を判断したい

自分が送る依頼: 調査を依頼 → 採用するか判断 → 残したい場合は記録を依頼。

自動で使われる skill: `research`、`critical-thinking`。記録を頼んだ場合は `record-decision` も使われます。

設定ファイルの検証にライブラリ X を使うか迷っています。
公式情報と今のプロジェクトの条件を比べ、採用を決めた理由も後から参照できるようにする例です。

## 1. 判断したいことと条件を伝える

```text
設定ファイルの検証にライブラリ X を採用すべきか調べてください。
公式情報を確認し、今の実行環境との互換性、既存コードへの影響、
導入しない案も含めて判断材料を出してください。まだ依存関係は追加しないでください。
```

X は、実際の候補名に置き換えます。守りたい条件があれば添えてください。
外部情報の確認には `research`、採用方針の前提確認には `critical-thinking` が使われます。

返答では、採用できる条件、根拠のリンク、推測や未確認事項を確認します。
例えば、既存の実行環境への対応が未確認なら、そのまま採用を決めずに確認を頼みます。

```text
今使っている実行環境でも動くことが、採用の条件です。
対応するバージョンを公式情報で確かめてから、比較を更新してください。
```

## 2. 採用するかを決める

例えば、互換性を確認でき、手書きの検証を減らせると判断したなら、結論を伝えます。

```text
今回は X を採用します。今の実行環境で使え、検証の重複を減らせるためです。
ただし、公開する設定ファイルの形式は変えません。
```

採用を決めただけでは、導入作業や判断の保存を頼んだことにはなりません。

## 3. 必要なら、判断を本人用に残す

後から理由を参照したければ、明示的に保存を頼みます。

```text
この採用判断と理由、見送った案、公開形式を変えない制約を本人用に記録してください。
```

`record-decision` が使われ、確認できた判断だけが本人用のローカル領域に保存されます。
記録はリポジトリ外に置かれ、PR や共有文書には加わりません。
保存を頼まなければ、記録は作られません。

同じ PC とリポジトリで理由を取り戻したいときは、次のように尋ねられます。

```text
設定ファイルの検証に X を採用した理由を教えてください。
現在の条件でも、その判断を使えるか確認してください。
```

## 完了の目安と次の依頼

採用するか、その理由と制約を根拠つきで説明できれば、判断は完了です。
記録も頼んだ場合は、何を保存したかを確認します。
導入する場合は「この判断に沿って X を導入し、検証してください」と別に依頼します。
