# 新しい機能を追加したい

自分が送る依頼: `$define → $design-interface` → 設計に合意して実装を依頼。

自動で使われる skill: `tdd`、`verify-change`。

完了したタスクが増えて一覧が見づらくなりました。
解決方法はまだ決めていません。欲しい状態を相談し、納得した形で実装まで進める例です。

## 1. 何を作るか相談する

```text
$define
タスク一覧が、完了したタスクで埋まって見づらくなっています。
未完了のタスクを見つけやすくしたいです。まず欲しい状態を整理してください。
```

`define` は、困りごとを確かめ、必要な判断を相談して、短い仕様にまとめます。
この段階では実装しません。

例えば、完了したタスクを隠す案が出たら、削除と表示切り替えの違いを確認します。

```text
完了したタスクは削除せず、表示を切り替えたいです。
全件と未完了だけの表示を切り替える仕様で進めましょう。
```

## 2. コードの使い方や形を先に決める

自分でも名前や型の意味を説明できるよう、同じ会話で次を頼みます。

```text
$design-interface
合意したタスク一覧の絞り込みについて、呼び出し側の使い方から設計してください。
名前、型、処理の分け方を、実装前に確認したいです。
```

使い方、型、名前の意図、別案との違いが提示されます。
例えば、表示条件を渡して一覧を取得する案なら、全件と未完了をどう指定するかを確認します。
合意するまで、実装は始まりません。

```text
提示された名前と型で進めてください。
全件表示と未完了だけの表示を切り替えられるよう、実装と検証をお願いします。
commit・push は不要です。
```

この合意を受けて実装へ進みます。コード変更には `tdd`、検証には `verify-change` が自動で使われます。
この 2 つを呼ぶために、依頼を追加する必要はありません。

## 完了の目安と次の依頼

全件と未完了だけの表示を切り替えられ、完了したタスクも再表示できることを確認します。
変更内容と検証結果を理解できれば、この例の実装は完了です。
共有する場合は、[PR 作成の例](review-and-pr.md) を参照してください。

小さく明確な変更で、使い方や型を先に相談する必要がなければ、合意した仕様を添えて直接実装を頼めます。
機能が大きく、他の人にも仕様を伝える必要があれば、[仕様書も作る例](large-feature.md) を使います。
