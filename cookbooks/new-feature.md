# 新しい機能を追加したい

自分が送る依頼: `$define` → 仕様に合意して実装を依頼。

自動で使われる skill: `what-breaks`、`tdd`、`prove-it`。

完了したタスクが増えて一覧が見づらくなりました。
解決方法はまだ決めていません。欲しい状態を相談し、納得した形で実装まで進める例です。

## 1. 何を作るか相談する

```text
$define
タスク一覧が、完了したタスクで埋まって見づらくなっています。
未完了のタスクを見つけやすくしたいです。まず欲しい状態を整理してください。
```

`define` は、困りごとを確かめ、必要な判断を相談して、短い仕様にまとめます。
この段階では実装しません。

例えば、完了したタスクを隠す案が出たら、削除と表示切り替えの違いを確認します。

```text
完了したタスクは削除せず、表示を切り替えたいです。
全件と未完了だけの表示を切り替える仕様で進めましょう。
```

## 2. 合意した仕様で実装を頼む

仕様に納得したら、同じ会話で実装を頼みます。

```text
合意した仕様で、実装と検証をお願いします。
commit・push は不要です。
```

型、関数名、処理の分け方などの内部の設計は、エージェントが決めます。
合意した仕様を変える必要が出たときだけ、作業を止めて確認されます。

書き換える前の影響調査には `what-breaks`、コード変更には `tdd`、検証には `prove-it` が自動で使われます。
この 3 つを呼ぶために、依頼を追加する必要はありません。
`prove-it` は、検証の前に、エージェント自身の差分を点検して直します。
利用者から見える振る舞いが変わる場合は、実装したエージェントとは別の subagent が、要求から検証条件を立てて動作を確かめます。
subagent を使えない場合は、実装したエージェントが要求から検証し直し、独立検証は未実施として報告します。

## 完了の目安と次の依頼

全件と未完了だけの表示を切り替えられ、完了したタスクも再表示できることを確認します。
完了報告で、重要な設計判断とその理由、検証結果、未解決の問題を理解できれば、この例の実装は完了です。
共有する場合は、[PR 作成の例](review-and-pr.md) を参照してください。

公開 API やデータの形式など、リポジトリの外から依存される形を決める必要があれば、
実装の前に `$design-interface` を使います。[仕様書も作る例](large-feature.md) に流れがあります。
機能が大きく、他の人にも仕様を伝える必要がある場合も、同じ例を使います。
