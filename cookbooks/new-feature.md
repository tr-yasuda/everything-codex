# 新しい機能を追加したい

自分が送る依頼: `$align` → 認識を合わせて実装を依頼。

自動で使われる skill: `what-breaks`、`tdd`、`prove-it`。

完了したタスクが増えて一覧が見づらくなりました。
解決方法はまだ決めていません。困りごととゴールの認識を合わせ、納得した形で実装まで進める例です。

## 1. 認識を合わせる

```text
$align
タスク一覧が、完了したタスクで埋まって見づらくなっています。
未完了のタスクを見つけやすくしたいです。まず、私の理解が合っているか確認してください。
```

`align` は、エージェントの理解を言い返し、ユーザーがズレを訂正して、
同じ認識になったら短く残します。
この段階では実装しません。

例えば、エージェントが「完了したタスクを削除する」と理解したら、
削除せず表示を切り替えたいことを伝えます。

```text
完了したタスクは削除せず、全件と未完了だけの表示を切り替えたいです。
その認識で合っていますか。
```

## 2. 認識が合った状態で実装を頼む

認識が合ったら、同じ会話で実装を頼みます。

```text
合意した内容で、実装と検証をお願いします。
commit・push は不要です。
```

型、関数名、処理の分け方などの内部設計は、エージェントが決めます。
合意した内容を変える必要が出たときだけ、作業を止めて確認されます。

書き換える前の影響調査には `what-breaks`、コード変更には `tdd`、検証には `prove-it` が自動で使われます。
この 3 つを追加で呼ぶ必要はありません。
`prove-it` は、検証の前に、エージェント自身の差分を点検して直します。
実装中に済ませた検証は結果を引き継ぎ、足りない確認と、その後の変更が影響する範囲を追加で確かめます。
利用者から見える振る舞いが変わる場合は、実装したエージェントとは別の subagent が、要求から検証条件を立てて動作を確かめます。
subagent を使えない場合は、実装したエージェントが要求から検証し直し、独立検証は未実施として報告します。

## 完了の目安と次の依頼

全件と未完了だけの表示を切り替えられ、完了したタスクも再表示できることを確認します。
完了報告で、重要な設計判断とその理由、検証結果、未解決の問題を理解できれば、この例の実装は完了です。
共有する場合は、[PR 作成の例](review-and-pr.md) を参照してください。

機能が大きく、他の人にも仕様を伝える必要がある場合は、
[仕様書も作る例](large-feature.md) に流れがあります。
