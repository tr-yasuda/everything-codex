# 大きめの機能を、仕様を固めてから作りたい

自分が送る依頼: `$define → $write-spec → $design-interface` → 設計に合意して実装を依頼。

自動で使われる skill: `tdd`、`verify-change`。

個人用のタスク管理に、チームで共有する機能を追加したい例です。
誰が見たり編集したりできるかなど、実装前に決めて文書に残すことがあります。

## 1. 作る範囲を決める

```text
$define
個人用のタスク管理に、チームでタスクを共有する機能を追加したいです。
まず、欲しい状態と今回作る範囲を整理してください。
```

共有相手、閲覧・編集できる範囲、今回は扱わないことなどを相談します。
例えば「同じチームの全員が閲覧でき、担当者だけが編集できる」範囲で合意したとします。

## 2. 合意した内容を仕様書にする

```text
$write-spec
合意したチーム共有機能を、他のメンバーにも説明できる仕様書にしてください。
保存先は既存の仕様書に合わせ、置き場がなければ相談してください。
```

最初に文書の全体像を確認し、そのあと一部分ずつ内容を相談します。
合意した部分からファイルに書かれます。最初から完成した仕様書が一括で作られるわけではありません。

例えば、担当者以外が編集しようとしたときの動きが抜けていれば、その場で補います。

```text
担当者以外は内容を見られますが、更新はできないようにしたいです。
画面だけでなく、直接更新を要求した場合も拒否する仕様を加えてください。
```

各部分に納得したら、仕様書を仕上げます。この時点ではアプリケーションの実装は始めません。

## 3. 使い方や型を決めてから実装する

```text
$design-interface
合意したチーム共有の仕様書をもとに、使い方、型、名前、モジュールの分け方を設計してください。
実装前に、それぞれの意図を確認したいです。
```

提示された形を確認し、変更したい点があれば伝えます。
納得したら、実装へ進むことを伝えます。

```text
この形で実装と検証をお願いします。
閲覧できる人と編集できる人の違いが、仕様どおり守られることも確認してください。
commit・push は不要です。
```

実装には `tdd`、完了前の検証には `verify-change` が自動で使われます。
どちらも、追加で呼ぶ必要はありません。

## 完了の目安と次の依頼

共有できる範囲と権限を仕様書から説明でき、実装もその仕様どおりに検証されていることです。
仕様を文書化するだけが目的なら、仕様書を仕上げたところで終えられます。
共有する場合は、[PR 作成の例](review-and-pr.md) を参照してください。
