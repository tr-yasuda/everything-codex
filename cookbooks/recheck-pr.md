# 自分が指摘した PR を再確認したい

自分が送る依頼: `$recheck-pr` → 返信案を確認して承認。

呼び出し後の処理: 指摘の解消を確認 → resolve → 修正差分の見直し → 返信案 → approve。

他の人の PR をレビューして指摘を投稿したあと、相手が修正や返信をしてきた場面で使います。
対象のプロジェクトを開き、PR 番号と、GitHub の認証・権限があることを確認します。
下の `pr#123` は、対象の PR 番号に置き換えてください。

## 依頼する

```text
$recheck-pr pr#123
```

自分のアカウントで立てたスレッドだけを対象に、指摘が直っているかを PR の最新のコードで確かめます。
直っていて、相手の質問や反論が残っていないスレッドは、確認なしで resolve されます。
前回のレビュー以降の差分も見直し、修正が新しい問題を入れていないかを確かめます。

相手が自分で resolve したスレッドも、直っているかを確かめます。
他の reviewer が立てたスレッドには触れません。コードの修正や commit・push も行いません。
手元の作業ツリーのブランチも切り替えません。

スレッドの resolve には、PR の作成者であるか、対象リポジトリへの書き込み権限が必要です。
resolve できなかった場合は、approve されずに理由が報告されます。

## 結果を確認して次へ進む

approve されたかと、resolve された件数が 1〜2 行で返ります。
直っていない指摘や、修正差分で見つかった問題など、自分の対応が要るものだけが続けて報告されます。
修正差分で見つかった問題は PR に投稿されません。投稿するかは自分で決めます。

相手の質問・確認・反論が残っているスレッドは、指摘が直っていても resolve されず、返信案が返ります。
返信は、文面を確認して承認するまで送信されません。

```text
提示された返信案をすべて、その文面で送信してください。
```

一部だけ送る場合は、承認する返信案を指定します。
返信文を変えたい場合は、変更した文面を伝えます。返信が不要なら、そう伝えます。

返信の送信後、指摘が直っているスレッドと、返信で指摘を取り下げたスレッドは resolve されます。
相手の返事を待つ返信を送ったスレッドは、開いたままです。

## approve について

自分の立てたスレッドがすべて解消し、返信も済み、修正差分に新しい問題がなければ、確認なしで approve されます。
approve は、確認した commit に付きます。確認のあとに相手が push していた場合は、approve されません。

Draft の PR や、auto-merge が有効な PR なども approve されません。
approve されなかった場合は、理由が報告されます。
approve しない条件の一覧は、[recheck-pr の Approve](../skills/recheck-pr/SKILL.md#approve) にあります。

## 完了の目安

approve されたか、残っているスレッドと approve されなかった理由を把握できていることです。
相手が再度修正や返信をしたら、同じ PR に `recheck-pr` をもう一度呼べます。

## PR の指定を省略できる場合

現在のブランチに対応する PR が対象なら、`pr#123` を省略できます。
別のリポジトリなら、`owner/repo#123` の形で指定します。
