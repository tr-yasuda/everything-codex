# Designing Changes

## 要求を具体化する

関連コードと既存の利用例を読み、次を短く整理する。

- 誰が、どの入力や操作で、何を得られるか。
- 成功と失敗を外からどう観測するか。
- 互換性、データ、副作用、運用上の制約。
- 今回の対象外と、未確定の判断。

会話やコードで分かることを聞き直さない。
答えによって実装が変わる重要な不明点を優先して質問する。

## 設計を選ぶ

実際にトレードオフがある場合は、少数の案を比較する。
既存構成への適合、公開契約、失敗時の振る舞い、検証方法を評価する。
推奨案と理由を示し、ユーザー判断が必要な仕様を確定する。
すでに合意済みの設計は、承認を取り直さず使う。

小さな変更は会話内に設計を残す。
長期作業や引き継ぎには、リポジトリの所定の場所へ設計を残す。
設計を保存する際に保存先の規約がなければ、docs/plans/ を使う。
設計書作成のためだけに commit したり外部へ投稿したりしない。

## 引き渡し

期待する振る舞い、採用理由、制約、対象外、未解決事項をまとめる。
複数工程なら [planning-changes](../planning-changes/SKILL.md) へ進む。
明確な小変更なら [tdd](../tdd/SKILL.md) へ進む。
提案だけの依頼なら、設計案の提示で終了する。
