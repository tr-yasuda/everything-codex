# Coordinator

## 目的と適用

複雑な作業を分解し、独立して進められる作業を Subagent に積極的に委譲して、全体の効率と品質を高める。
設計、実装、テスト、レビュー、調査、デバッグ、Issue 対応、PR 作成など、用途は限定しない。

協調が有効な作業では、ユーザーに言われるのを待たずに使う。手動でも呼び出せる。
Codex CLI では `$coordinator`、Claude Code では `/coordinator` に続けて依頼を書く。
この skill を適用しても、Subagent は独立性と効果を判断してから起動する。
短い修正や、分割すると調整の負担が増える作業では、適用しても Subagent を起動しなくてよい。

Root Agent は全体の計画、委譲、依存関係の調整、進捗管理、成果物の統合、最終検証に責任を持つ。
Root は委譲・調整・統合を優先し、大きな実装を自分で抱え込まない。
ただし、委譲の説明や待機より自分で進める方が早い場合などは、Root が担当してよい。

## 実行環境を確かめる

起動前に、現在のハーネスが公開する機能、権限、実行中のエージェントと利用可能なリソースを確認する。
特定のツール名、コマンド、モデル、事前定義された役割があることを前提にしない。
環境に応じて次の補足を読む。補足と実行中の仕様が異なる場合は、実行中の仕様を優先する。

- Codex CLI: [Codex CLI の補足](references/codex.md)
- Claude Code: [Claude Code の補足](references/claude-code.md)

起動、通信、待機、停止にはハーネスの標準機能を使う。
使えない機能を有効にするため、設定や権限を自動変更しない。
人数、階層の深さ、役割、実行方式に、この skill 独自の固定制限は設けない。
利用可能な機能や上限が不明な場合は、使えると推測せず、その範囲を確かめる。

## 分解して委譲する

### 作業と依存関係を整理する

依頼と完了条件をもとに、個別に成果を返せる作業を洗い出す。
各作業が必要とする入力、先に確定すべき判断、共有する変更対象や実行環境を確かめる。
依存する作業と、互いの途中結果を待たずに進められる作業を分ける。

役割名やファイルの数だけで分割しない。
例えば、同じ振る舞いの実装と、それができて初めて動かせるテストは、同時に完成させる独立作業ではない。
一方、別の機能の実装や独立した資料調査は、必要な契約や前提が揃っていれば並行して進められる。

### 独立した作業を並列投入する

先行作業を待つ必要がなく、成果を渡す負担より並列化の効果が大きい作業を Subagent に委譲する。
役割は作業に合わせて決め、調査だけでなく、範囲を明確にできる実装も委譲する。
Root は調整・統合を続けられる範囲で、待ち時間を減らす作業や短い修正を担当する。
委譲した作業を Root が同じ範囲でやり直すことは避ける。成果の確認は別途行う。

同時実行数は、ハーネスの上限、既存の実行数、CPU・メモリ・利用枠、依存関係、調整コストから決める。
Subagent による再委譲も含めて考え、局所的に独立しているだけで起動数を増やさない。
枠が空いた場合や依存が解消した場合は、残りの作業を見直して追加で委譲する。
上限に達したときは、同じ起動を繰り返さず、実行中の成果を待つか、他の作業を進める。

### 委譲の内容を伝える

委譲前に、担当作業に適用される既存 skill とプロジェクトの指示を確認する。
各エージェントには、判断と実行に必要な次の内容を渡す。
会話全体の継承や、親が読んだ skill・資料の自動継承は前提にしない。
自動適用だけに頼らず、SKILL.md や指示ファイルのパス・節を渡し、適用される手順を実行させる。

- 目的と、全体の中で担当する成果
- 担当範囲と変更対象。共有環境で他の担当も作業していることと、他者の変更を戻さないこと
- 必要な背景、資料、確定済みの契約、先行作業の成果、未確定の前提
- 完了条件、必要な検証、返す成果物と根拠。実行できなかった確認も返すこと
- 作業場所、権限、適用されるプロジェクトの指示や専門手順、再委譲時に守る担当範囲

会話が分かれていることだけで、ファイルやポートなどの共有資源も分かれていると判断しない。
編集担当が重ならないようにし、共有契約を変える必要があれば、関係する担当へ知らせてから調整する。
同じファイルなどを別々に編集する必要がある場合は、編集順序を決めるか、Worktree などで分離する。
分離時は、基点と未 commit の変更の扱いを確認し、成果を戻す場所と統合担当を決める。
プロセス、ポート、テスト用データなど、ファイル以外の共有資源にも競合がないか確かめる。

### 再委譲する

Subagent も、担当する作業がさらに独立した成果へ分かれる場合は、下位の Subagent に委譲してよい。
再委譲する親は、同じ原則で範囲を分け、下位の成果を確認・統合してから自分の結果を返す。
同じ依頼をそのまま下位へ渡して委譲を繰り返さず、担当範囲を具体的に分ける。
担当範囲外の依存関係や競合、全体のリソースに関わる問題は、委譲元へ知らせる。

## 進捗を確認して調整する

Root は、次の判断に必要な範囲で、担当、依存先、進行状況、成果物、未解決の問題を把握する。
ハーネスのタスク一覧や通知があれば利用し、同じ情報を独自の台帳へ重複して記録しない。
全員の完了を待つ必要はない。返された成果を確認し、依存が解消した後続作業から進める。
待機には標準の通知・待機機能を使い、変化のない状態を短い間隔で確認し続けない。

新しい依存関係、仕様の食い違い、競合、失敗、停滞が見つかった場合は、影響する作業を見極める。
必要な担当へ伝え、作業を止める、範囲を分け直す、担当や順序を変えるなどして調整する。
再割り当ての前には、以前の担当の実行状態と途中成果を確かめ、同じ対象で作業が並走しないようにする。
古い前提に基づく結果を、その後の成果の根拠として使わない。

利用できない機能は、次のように代替する。

- 再委譲できない: 委譲元へ追加の分割案を返し、起動できる親が引き取る
- エージェント同士で通信できない: 親が必要な結果や変更を中継する
- 分離できない: 担当範囲を分けるか、競合する編集・操作を直列にする
- Subagent を起動できない: 自分で進める。並列実行や独立検証をしたとは扱わない

代替しても確かめられないことや、進められないことは、理由と影響を報告する。

## 統合して完了を確かめる

Subagent の完了報告だけでは、作業を完了扱いにしない。
成果物と提示された根拠を読み、担当範囲と完了条件を満たすか確かめる。
適用される skill とプロジェクトの指示に従ったかも確かめる。
不足や食い違いがあれば、追加確認や修正を依頼するか、Root 自身で補う。
意図的な独立レビューなどを除き、重複作業は整理し、矛盾する結果は根拠を比べて解消する。

Root は成果物を統合し、統合後の状態で依頼全体の完了条件と必要な検証を確かめる。
各担当の検証が通っていても、組み合わせた結果が正しいとは限らない。
変更後の成果に適用できない古い検証結果は使わず、未完了の作業や実行中のエージェントを残して完了としない。
作業用のエージェントや環境は、成果を保全したうえで、ハーネスが提供する方法で終了・整理する。

最終報告には、得られた成果、実際に確かめたこと、残る問題や未確認事項を書く。
協調の制約が結果に影響した場合は、その影響も示す。

## 既存の指示・skill との協調

この skill は分解・委譲・並列実行・統合を担当し、既存 skill が定める実装・検証・レビューの手順を置き換えない。
他の skill の導入は必須にしない。
専門手順に必要な直列処理やレビューの独立性を、並列化や情報共有のために崩さない。
既存 skill が定める作業範囲とユーザー承認の条件は、再委譲先にも引き継ぎ、変更しない。
委譲は元の依頼の範囲と権限内で行い、外部への投稿などの許可を広げない。
起動・通信・タスク管理の再実装や、独自の実行基盤は作らない。
