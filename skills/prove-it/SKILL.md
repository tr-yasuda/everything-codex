# Prove It

## 目的

完了を報告する前に、自分の差分を点検して直し、変更が想定どおりに動くことを実際に確かめる。

テストや型チェックが通っても、利用者が使う経路で動くとは限らない。
確かめずに「動くはず」と報告しない。

代表的な入力や状態で一度成功しただけでは、確かめたことにしない。

この skill は、ユーザーに言われるのを待たずに使う。

## 使うタイミング

- コードや設定を変更し、完了を報告する前
- 変更が動くかどうかを聞かれたとき。自分が変更していない場合も含む

動作を問わない調査や質問への回答では使わない。

## 渡す前の点検

自分が変更した場合は、確かめる前に、今回の作業で自分が加えた差分を読み直して直す。
未整理のまま渡すと、処理を追い、文章を読み解く負担が、レビュアーや利用者へ移る。

次を直す。

- 追いにくいコード: 呼び出し元から、判断、状態の変更、副作用の順序、結果、失敗時の扱いを追えない箇所。
  処理の理解に必要な判断を隠している、不要なラッパーや間接層
- 不要なコメント: コードから分かる手順や要約、作業ログ
- 他人が読む文章: 手順書やコードコメントなどにある、読み手の判断・実行に使わない経緯、細部の列挙、繰り返し

直す範囲は、次のとおりにする。

- 今回の作業で自分が加えた差分の中だけを直す。周辺のコードは変えない
- ユーザーや他の人が書いた部分と、作業の前からあった未 commit の変更は変えない。
  自分の差分と区別できなければ、変えずに報告する
- 振る舞いと、ユーザーと合意した契約や文面は変えない

レビューの対象は、今回の作業で加えた差分のうち、まだレビューしていない部分にする。
1 回目は差分全体、2 回目以降は前回のレビューより後で加えた差分が対象となる。
レビューのあとの変更が、テストで見つからない問題を新たに入れることがあるため、修正のきっかけで対象を限らない。
確かめた結果、戻した変更は対象に含めない。

対象が次のどれかに触れる場合は、reviewer にレビューさせる。

- 認証・認可、外部入力の検証
- データの保存・削除・移行
- 並行処理、retry、transaction
- リポジトリの外の利用者やシステムが依存する形
- 複数のモジュールにまたがる処理の流れ

reviewer には、対象に加えて、影響を受ける呼び出し元・呼び出し先・関連するテストを読ませる。
自分の結論は渡さず、独立して読ませる。
観点は、正しさと、上のうち対象が触れるものだけにする。
reviewer を使えない場合は、自分が同じ観点で読み直してレビューの代わりにし、使えなかったことを報告に書く。
レビューの回数に上限は設けない。

指摘は、発生条件、処理経路、影響をコードで確かめられたものだけを扱う。

- 今回の自分の差分が原因の指摘は、言われるのを待たずに直す
- 合意した仕様や契約を変える必要がある指摘と、今回の差分以外が原因の指摘は、直さずに報告する

1 回のレビューや確認で見つかった問題は、まとめて直してから Workflow で確かめる。
レビューは、テストや動作確認の代わりにしない。
Workflow を終えたあとにコードを変えた場合は、変えた部分を Workflow の手順 1 から確かめ直す。

## Workflow

1. 確かめる振る舞いを決める
2. 確かめる条件を決める
3. 確かめ方を決める
4. 期待する結果を先に決め、実行して観察する
5. repository で要求されるテスト・型チェック・lint・build を実行する
6. 後片付けをする
7. 結果に応じて、報告するか問題を直す

### 1. 確かめる振る舞い

- 依頼で求められた振る舞い
- 変更が影響する既存の振る舞い
- バグ修正の場合は、元の再現手順

### 2. 確かめる条件

振る舞いごとに、それが成立すべき入力・状態・操作順序を、次の観点で挙げる。

- 境界値: 上限、下限、0 件、1 件、最大件数
- 空や異常な入力: 未入力、不正な形式、想定より長い値
- 事前の状態: 初回、データが既にある、前の操作が途中で中断された後
- 操作の順序と繰り返し: 順序の入れ替え、同じ操作の再実行、同時の操作
- 途中の失敗: エラーの伝わり方、中途半端に残るデータ

挙げた条件から、今回の変更が触れる範囲にあり、壊れたときの影響が大きいものだけを選ぶ。

### 3. 確かめ方

変更の影響を確かめられる方法のうち、最も軽いものを選ぶ。

- 利用者が使う経路に影響する変更: アプリケーションを起動し、CLI、API、画面の操作で確かめる
- モジュール間の契約に影響する変更: integration test や E2E test で確かめる
- 内部に閉じた変更: unit test、型チェック、lint で確かめる
- 文書だけの変更: repository が定める lint などで確かめる

迷った場合は、利用者に近い方法を選ぶ。

起動方法は、repository の指示、README、build 設定から判断する。
起動手順を定めた skill や文書があれば、それに従う。

起動する前に、接続先の設定を確かめる。
本番環境や実在の外部サービスに接続する設定なら、起動前にユーザーへ確認する。

#### 多数の入力で確かめる場合

入力の幅が広く、次のような性質を言えるロジックでは、Property-Based Testing で多数の入力を生成して確かめる。

- 変換して戻すと、元の値に戻る
- 書き換える前の実装と、結果が一致する
- 何度実行しても、結果が変わらない
- どんな入力でも、異常終了しない

repository に仕組みがなければ、実行できるテスト環境が既にあるときだけ、一時的に導入する。
標準機能で足りなければ、その言語で広く使われているライブラリを、開発用の依存関係として 1 つだけ追加する。
repository やユーザーの指示が、依存関係の追加を禁じるか確認を求めている場合は、追加しない。
導入したテストと依存関係は、確認が終わったら取り消す。

性質や入力の生成を簡単に書けない場合と、導入できない場合は、選んだ条件を個別に確かめる。

### 4. 実行と観察

通常の入力に加え、選んだ条件ごとに期待する結果を先に決め、実際の結果と比べる。

出力、終了コード、画面、ログに加え、保存されたデータや作成されたファイルも確認する。
今回の変更後に実行した結果だけを証拠にする。
一度でも失敗した結果は、再実行で通っても報告に残す。

### 5. テスト・型チェック・lint・build

repository で要求される項目を検証する。
手順 4 で同じ検証を済ませていれば、繰り返さない。

### 6. 後片付け

- 確認のために起動したプロセスやコンテナを止める
- 確認用に加えた一時的な変更を取り消し、変更したデータやファイルを元に戻す
- 取り消すのは自分が加えた差分だけにし、Git の破壊的な操作で戻さない

止められなかったものや残したものは、報告に書く。

### 7. 結果に応じた進め方

- 想定どおり: 報告する
- 想定と違う、または失敗した: 「問題が見つかった場合」に従う
- 実行できない: 「確かめられない場合」に従う

## 問題が見つかった場合

今回の作業で加えた変更が原因なら、言われるのを待たずに直す。
それ以外が原因なら、原因と直し方の案を報告する。直すかどうかはユーザーが決める。

直すときは、次に従う。

1. 原因を特定してから直す
2. 症状を抑えるだけの修正はしない
   例: 例外を握りつぶす、retry や sleep で失敗を隠す、テストの期待値を誤った実装に合わせる
3. うまくいかなかった修正は、次を試す前に戻す
4. 既存のテストで再現できない問題は、利用側から見える振る舞いを検証する回帰テストを追加する
5. 直したら、影響を受けた部分を Workflow の手順 1 から確かめ直す

## 止まる判断

次の場合は、直すのをやめてユーザーに報告する。

- 修正を試すたびに、問題が残るか別の箇所が壊れ、それが 3 回続いた。
  レビューの指摘のうち、修正と関係なく、修正前の差分にあった問題は数えず、それまでの数も戻さない
- 再現しない失敗で、原因を絞る手がかりがなくなった
- 依頼や既存の仕様を超えて、利用者から見える振る舞い、公開仕様、互換性、データの扱いを変える必要がある
- 権限や credentials が足りない
- 破壊的・不可逆な操作が必要になる

報告には、試したこと、それぞれの結果、分かったこと、残る仮説を書く。

## 確かめられない場合

依存関係の未インストールやローカルのサービスの未起動など、ローカルで解決できる不足は自分で解決する。

権限、credentials、外部サービスの不足は回避しない。次の順で対応する。

1. 最も近い代替手段で確かめる
   例: 外部境界を fake で置き換える、dry-run を使う、一部の経路だけを実行する
2. 確かめられなかった範囲と理由を記録する
3. ユーザーが確かめるための手順を報告に含める

## 判断の範囲

次のことは自分で判断して進める。

- 点検で直す箇所と直し方、reviewer に担当させる観点
- 確かめる振る舞い、条件、確かめ方
- Property-Based Testing を導入するかどうか
- テストデータ、一時ファイル、ローカルでの起動
- 技術的な直し方の選択

次のことはユーザーに確認する。

- 「止まる判断」に当てはまること
- 本番環境や外部サービスへの書き込みなど、外部に影響する操作
- 観察結果が仕様どおりか、既存の仕様や依頼から判断できない場合

## 報告

報告する前に、まだレビューしていない差分が「渡す前の点検」でレビューさせる条件に触れていれば、レビューさせる。
完了の報告は、直す指摘がなくなってからにする。
「止まる判断」で報告する場合は、指摘は直さず、報告に書く。

完了報告には、ユーザーが変更を理解するために必要な内容だけを、簡潔に書く。
次のうち、該当するものを分けて書く。作業の経過は書かない。

- 点検したこと: 直した点とその理由、直さずに残した指摘。
  reviewer を使った場合は、指摘がなくても、担当させた観点と結果を 1 行で書く。
  2 回目以降のレビューがあれば、読ませた範囲を同じ行に加える
- 確かめたこと: 実行したコマンドや操作と、観察した結果。条件は 1 件ずつ並べず、観点ごとにまとめる
  例: 「境界値と空の入力を `import` に渡し、どちらも終了コード 0 で保存件数が一致した」
- 原因と修正: 見つけた問題、その原因、直した内容。直していない場合は直し方の案
- 判断したこと: 自分で決めたことのうち、あとの変更や利用に影響する設計判断と、その理由。残す価値がある Property-Based Testing のテストは、ここで提案する
- 未確認のこと: 確かめられなかった範囲、理由、確かめる手順、一度だけ失敗した結果。
  選ばなかった条件は、壊れたときの影響が大きいものだけを書く

該当する内容がない項目は省略する。
credentials などの秘密情報や個人情報は、報告や出力に含めない。
