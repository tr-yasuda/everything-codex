# Unslop

この skill は明示的に呼び出された場合のみ使用する。

```text
$unslop
$unslop <対象差分>
```

- 対象の指定がなければ、現在の作業ツリーの変更を stage 済みの変更も含めて対象にする。
- 対象が指定されていれば、その差分を対象にする。差分を取得できない場合は推測で変更しない。

## 目的

対象差分に残った一時コードやデバッグ用コードを削除する。
変更意図に照らして説明できないものも削除する。
あわせて、関わる処理を人間が入口から結果まで追いやすい構造にする。
コード量、関数の短さ、抽象化の数を減らすこと自体は目的にしない。

## 判断基準

呼び出し元から、次の点を追えるかを確認する。

- 何を入力として受け取るか
- どの条件で何を判断するか
- いつ状態を変更し、どの副作用を起こすか
- 何を結果として返すか
- 失敗した場合に何が起きるか

処理の理解に必要な判断や副作用が、不要なラッパー、ヘルパー、間接層に隠れている場合は構造を見直す。
一方、独立した責務や安定した契約を表す境界は残す。必要なら新たに設けてもよい。
関数を短くするためだけの分割や、行数を減らすためだけの統合は行わない。
あわせて、一時コードやデバッグ用コードが残っていないかを確認する。
判断方法は「一時コードとデバッグ用コードの精査」に従う。

## 一時コードとデバッグ用コードの精査

対象差分と、判断に必要な周辺コードから、一時コードとデバッグ用コードを探す。
これらは、変更意図に照らして説明できない場合も、将来の保守対象として残さない。
特定の記号や書き方だけを目印にせず、そのコードが成果物の動作や理解に寄与しているかで判断する。
削除するか迷う場合は、変更意図、呼び出し元、テスト、コメント、Git 履歴を読む。

たとえば、次のようなものは一時コードまたはデバッグ用コードとして扱う。
一覧は例であり、これらに限らない。

- 調査、再現、確認のためだけの出力、分岐、固定値、待機、無効化、差し替え
- コメントアウトされたコード
- 使われていない一時的な変数、関数、ファイル
- 通常の経路に残ったテスト用の mock や stub、差し替え
- 変更意図に照らして説明できず、呼び出し元、テスト、コメント、Git 履歴にも存在理由が見つからないコード

削除すると通常の利用者向けの振る舞いや public API が変わる場合は、何が壊れるかを示して確認を取る。
public API や外部契約の一部だと分かったコードは、一時コードやデバッグ用コードではなく契約として扱う。
デバッグ時だけの出力や調査用の分岐などは削除してよいが、public API や外部契約の一部なら確認を取る。

## Workflow

1. 対象差分と変更意図を確認する。関連する呼び出し元、呼び出し先、テスト、既存コメントを読み、必要なら Git 履歴も読む。
2. 「一時コードとデバッグ用コードの精査」に従って、削除対象を特定する。
3. 主要な処理経路を入口から結果まで追い、理解の妨げとなる構造やコメントを特定する。
4. デバッグ時だけの出力や調査用の分岐は削除してよい。それ以外は、通常の利用者向けの振る舞いと public API を維持したまま、コードと関連コメントを変更する。削除で通常の振る舞いや public API が変わる場合は、何が壊れるかを示して確認を取る。
5. 関連するテスト、型チェック、lint などで検証し、コードとコメントの差分を見直す。

## コメントの精査

対象差分に関わる処理経路では、変更行の外にある既存コメントも確認する。
コメントの読み手は、次にそのコードを変更する保守者とする。
コメントの内容をコード、テスト、Git 履歴、外部との契約と照らし合わせ、次の基準で扱う。

- コードから分かる手順や要約、作業ログ、古くなった説明は削除または修正する。
- 一時コードやデバッグ用コードを残す理由を説明するだけのコメントは、コードと一緒に削除する。
- 読みにくい構造をコメントで補っている場合は、構造を見直す。
- 通常の実装が成立しない理由、不変条件、外部 API や互換性の制約、確認済みの性能制約、
  既知の問題と回避条件など、コードから読み取れない事実を残す。
- 残すコメントには、適用条件と無視した場合に壊れるものが分かるようにする。
- 根拠を、テスト・外部仕様・計測・既知の障害のどれで確認したかが分かるようにする。
- 公開インターフェースの契約を示す doc comment は、プロジェクトで正本として使う場合、その契約を保つ。

コメントは、その制約を脅かす変更が起きるコードの近くに置く。
関係ないファイル冒頭や離れた関数へ置かない。
Git 履歴は当時の変更理由を調べる材料に使うが、歴史的経緯をそのままコメントにコピーしない。
変更理由と作業経緯は、commit や PR description が担う。

コード上の名前や API 名はそのまま使う。ただし読み手が理解で止まる場合は、
短く日本語で説明する。たとえば重複実行を防ぐ識別子の名前を変えずに、
その識別子が防ぐ副作用を添える。専門用語を、曖昧さを隠す装飾には使わない。

根拠を確認できないコメントは推測で書き換えず、確認できなかった点を報告する。
新しいコメントも、コードだけでは分からず、将来の変更時に守る必要がある事実に限る。

## 変更時の制約

- 対象差分と、処理の追いやすさや一時コード・デバッグ用コードの判断に必要な周辺コードだけを変更する。
- 無関係な変更は、stage 済みのものも含めて保持する。
- デバッグ時だけの出力や調査用の分岐は削除してよい。それ以外は、入出力、エラー、検証、状態変更、副作用の順序、リソースの扱い、並行処理の意味を保つ。
- public API の名前、型、契約、互換性を変更しない。変更が必要な場合は、何が壊れるかを示して確認を取る。
- 明確な改善がない箇所は変更しない。ただし、一時コードやデバッグ用コードの削除は、この制約を理由に除外しない。

一時コードやデバッグ用コードの削除以外で、振る舞いを維持できる根拠が不足している場合は、既存テストと呼び出し側から契約を確認する。
必要なら関連する振る舞いをテストで固定してから変更する。
それでも安全に判断できない箇所は推測で書き換えず、理由を報告する。

## 完了時の報告

- 削除した一時コード・デバッグ用コードと、削除した理由
- 処理の流れがどのように追いやすくなったか
- 既存コメントをどう扱ったか、その理由
- デバッグ時だけの振る舞いを削除した場合は、その内容
- 通常の利用者向けの振る舞いと public API を維持した根拠
- 実行したテストや検証、その結果
- 削除しなかった一時コード・デバッグ用コードと、その理由
