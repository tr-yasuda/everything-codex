# Self-drive

## 目的と適用

複数の実装・調査タスクを、ユーザーが指定した範囲で自走して進める。
Codex CLI では `$self-drive <目標・タスク参照>` を使う。
Claude Code では `/self-drive <目標・タスク参照>` を使う。

この skill は自走の入口であり、coordinator の分解・委譲・統合、各 skill の実装・検証・承認条件を置き換えない。
対象タスクが完了するか、ユーザーが自走の停止を求めたら、実行中の subagent を停止させてから、このモードを終了する。
subagent には、ハーネスが提供する方法で停止を伝え、終了を確認する。
停止できなかった subagent と確認できた途中成果は、報告に含める。
ユーザーの判断が必要なときは、判断材料を示して同じ手順で作業を止める。
ユーザーが判断を示し、元の依頼の範囲・権限・承認条件が変わらない場合は、同じ依頼の続きを再開する。
範囲・権限・承認条件が変わる場合は、変更後の依頼として確認してから進める。
自走では、元の依頼の範囲・権限・承認条件を広げない。

## タスクの確認と選択

ユーザーが指定した現在の情報源（依頼文・Issue・Jira など）を、タスクの正本として確認する。
接続済みツールで現在の状態を読める場合はそれを使い、読めない場合はユーザーにタスク一覧や内容の提供を求める。
過去の会話や記憶だけを正本として扱わない。
複数の依頼を含むときは、それぞれ独立して検証し、Draft PR にできる単位へ分解する。
実装と、その実装ができて初めて実行できる検証は、同じタスクとして扱う。

対象タスクを選ぶ前に、次を確認する。

- タスクの現在の内容、完了条件、依存関係、競合するファイルや共有資源
- 実行環境、接続済みツール、利用できる profile と subagent の制約
- 並列化できる作業と、直列に進めるべき作業
- 元の依頼に含まれる権限と、既存 skill が求めるユーザー承認

Issue や Jira の状態更新、担当者の変更は、明示的に依頼されない限り行わない。
Draft PR の作成・更新は、この skill の既定の実行範囲に含める。
タスク管理システムの状態をラン記録へ複製せず、再開に必要な参照と結果だけを保存する。

## ラン記録

ラン記録は再開用の作業メモであり、タスクの正本を置き換えない。
`$self-drive` を開始するとき、`$CODEX_HOME/self-drive/<project-slug>/<run-id>/` にラン記録を作成する。
`CODEX_HOME` が未定義のときは `~/.codex` を使う。
作業ツリーやリポジトリ内へ保存しない。
この場所はリポジトリ外の本人用領域で、PR や commit の対象にしない。
保存先に書き込めない場合は、リポジトリ内へ保存せず止まる。
ラン記録の入口は `run.md` とし、元のタスク参照と対象リポジトリの root を最初に記録する。
同じ元のタスク参照に対応する未完了のラン記録があれば、新しい記録を作らずその内容を確認する。

ラン記録には、次の内容だけを保存する。

- タスクの目的、完了条件、依存関係、現在状態
- 担当 worktree、branch、PR の参照
- 実行した検証と観察結果
- 判断が必要な地点と判断材料
- 次にすべきことと未解決事項

`run.md` には、人間が現在の判断と次の操作を読める要約を書く。タスクごとの詳細は同じディレクトリに置く。
生の会話ログ、巨大なコマンド出力、credentials、secrets、個人情報は保存しない。
ラン記録は PR・commit・リポジトリ内ファイルには含めない。
タスクの割り当て、検証結果、判断、統合、PR 作成のいずれかが変わったら更新する。
token 上限やサーバー障害で会話が失われても、この記録から再開できる形を保つ。

## 進め方

独立して進められる作業は coordinator を使って分担する。
coordinator や適用する既存 skill を使う前に、その `SKILL.md` が現在の環境で読めるかを確認する。
必要な skill が読めない場合は、その導入を案内し、推測して手順を代替せず止まる。
coordinator に渡す依頼には、元の目的、担当範囲、完了条件、適用されるプロジェクト指示と skill、承認条件、必要な結果と根拠を含める。
書き込み担当ごとに worktree / branch を1つ割り当てる。同じ checkout で書き込み担当を並行させない。
統合は Root が直列で行い、統合後の状態を改めて検証する。
同時実行数は 20 を上限とし、独立性、CPU・メモリ・API の利用枠、依存関係、統合能力から実際の起動数を決める。
上限は常に使い切る目標ではなく、空いた枠へ残りの独立作業を追加する。

Subagent を使うときは、対象 profile の現在の設定と指示から、使用できる reasoning effort とその意味を確認する。
タスク難易度から effort への共通変換表を持たない。

- profile が effort を固定している、既定値を変えている、使用できる値が異なる場合は、その定義に従う。
- 専用 profile の指示が共通指示を置き換える場合は、profile 固有の選択基準と使用できる値を委譲文に引き継ぐ。
- effort が未定義・未対応・あいまいなときは、推測して置き換えず、ユーザーに確認する。

推論量を変えるためにモデルを切り替えない。

各タスクでは、適用条件が成立している既存 skill を使う。
実装・修正では最小限の変更を保つ。
コードを変更する前は `what-breaks`、失敗の原因を調べるときは `root-cause`、実装は `tdd` を適用する。
ユーザーが `unslop` を明示的に求めたときだけ、対象差分を指定して使う。
コードや設定を変更したタスクの完了前は `prove-it` に従い、差分と実際の動作を確認する。
各担当の完了報告だけを根拠にせず、成果物と検証結果を確認してから統合する。

## PR

検証が通った書き込みタスクごとに、その worktree で `$create-pr` を実行し、Draft PR を作成または更新する。
`$self-drive` の呼び出し自体を、選択したタスクに対する `$create-pr` の明示的な呼び出しとして扱う。
`create-pr` の検証、commit・push、Branch、PR body の規則を置き換えない。
検証が失敗したタスクは PR を作成・更新せず、失敗と次の判断材料をラン記録と報告に残す。
merge・Issue close・Jira の状態変更は、ユーザーが明示的に依頼しない限り行わない。

## 再開

ラン記録から再開するときは、記録だけを信用しない。
Git branch・PR・Issue / Jira の現在状態を読み、記録と食い違う部分を明示してから扱う。
古い検証結果は、現在の差分に適用できるか確認する。適用できない結果は根拠にしない。
記録と現在状態が矛盾して進められない場合は、矛盾点と判断材料を示して止まる。

## 止まる判断

次のいずれかに当たるときは、自走を続けずに判断材料を示してユーザーに確認する。

- 利用者から見える振る舞い、公開インターフェース、互換性、データの扱いで選択肢が複数ある
- 仕様や完了条件が不明確、またはタスク間で矛盾する
- effort の定義が使えない
- 破壊的・不可逆な操作、Draft PR 以外の外部への投稿、Issue や Jira の状態変更が必要になる
- 権限、認証、機密情報の扱いが不明確になる
- 必要な検証ができない、または検証結果が矛盾する

確認を求めるときは、選択肢ごとの影響、推奨、推奨しない理由、確かめていないことを示す。

## 完了報告

完了したタスク、実際に確認したこと、実行した検証、残っているタスク・判断・未確認事項を報告する。
タスク管理システムや外部サービスの状態は、確認できた範囲で現在の状態を報告する。
ユーザーが明示的に依頼した更新をした場合は、その操作と結果も報告する。
