# Test-Driven Development

## コア原則

テストは、公開インターフェースを通じて振る舞いを検証する。
内部構造だけの変更で壊れず、契約の破壊で失敗するテストを書く。
公開インターフェースとは、対象モジュールの利用側から見える契約を指す。
すべてのテストをアプリ全体の E2E テストにする必要はない。

1 つの振る舞いについて、RED → GREEN → REFACTOR を完了してから次へ進む。
全テストを先に書いてからまとめて実装する horizontal slicing は行わない。
次のテストは、前のサイクルで得た知見をもとに決める。

**GREEN は中間状態です。REFACTOR の点検と判断が済むまで、
次のテスト、タスク完了、完了報告へ進んではいけない。**

## 準備

要求、既存コード、テストコマンドを確認する。
テスト対象の振る舞いを優先順に列挙し、最初の 1 つを選ぶ。
重要な経路と複雑な判断に集中し、すべての組み合わせを網羅しようとしない。
仕様や互換性に重要な未決事項がある場合はユーザーに確認する。
すでに明確な依頼に対し、計画承認を取り直さない。

既存のテストを実行して、開始時点の状態を確認する。
文書、生成物、静的な設定など、自動テストが適さない変更には
対象に合う検証を選び、TDD を実施したとは報告しない。

## 各サイクル

### 1. RED

利用側から見た 1 つの振る舞いを説明するテストを書く。
「どの振る舞いが壊れたら、このテストが落ちるか」を説明できるようにする。
実行して、期待する振る舞いが未実装であるために失敗したことを確認する。
環境不備、typo、無関係な例外による失敗を RED の証拠にしない。
最初から成功する場合は、既存機能を確認しているのか、検証が弱いのか調べる。

最初のテストは tracer bullet として、選んだ境界を通る経路を成立させる。
private メソッドや内部呼び出し順を契約の代わりに検証しない。
時刻や外部サービスなど、制御が必要な境界では代替を使える。
その場合も、モック自身の設定ではなく対象の振る舞いを検証する。

### 2. GREEN

現在のテストを通す最小実装を書く。
将来のテストの先回りや、関係のない改善を混ぜない。
対象テストと影響する既存テストを実行して、成功を確認する。
RED のままリファクタリングを始めない。

成功したら、直ちに次の REFACTOR へ進む。
テスト成功だけを理由に、サイクルを閉じない。

### 3. REFACTOR

**設計の点検は毎回必須。コード変更の要否は点検して判断する。**

直前に変更した実装、テスト、周辺コードを読み直し、次を点検する。

- 重複: 同じ判断や知識を複数箇所に書いていないか。
- 責務・依存: 副作用と判断が不必要に混ざっていないか。
- 公開契約と命名: 利用側の理解が難しくなっていないか。
- テスト: 実装詳細に依存せず、意図が読めるか。
- 最小性: 現在の要求で説明できない抽象化や分岐がないか。

改善が必要なら、振る舞いを保つ小さな変更を 1 つずつ行う。
各変更後に対象と関連テストを実行し、GREEN を維持する。
失敗したら、その変更を修正するか自分の変更だけを戻して再検証する。
新しい振る舞いが必要になった場合は、この工程に混ぜず次の RED に回す。

変更不要と判断する場合も、対象と理由を具体的に残す。
「問題なし」「テストが通る」「小変更だから」だけでは点検結果にならない。
点検した結果、変更がない場合は、直前の GREEN の検証結果を使える。
記録を作るためだけに、無用な抽象化やファイル分割を追加しない。
範囲外の改善は残件に分け、今回の完了条件に必要な改善を先送りしない。

### 4. サイクルを閉じる

会話内の進捗記録、または既存の作業計画に、次の証拠を短く残す。
専用のログファイルを毎回作る必要はない。

```text
振る舞い: 空のメールアドレスを拒否する
RED: 対象テストが「拒否されず成功した」ため失敗
GREEN: 最小修正後、対象と関連テストが成功（コマンドと結果）
REFACTOR: 入力判定とテストを点検。重複する空文字判定を共通化
再検証: 対象と関連テストが成功（コマンドと結果）
```

変更しない場合は、次のように記録する。

```text
REFACTOR: 入力判定とテストを点検。判定は 1 箇所で副作用もなく、
名前が契約を表しているため変更不要。検証は直前の GREEN を使用
```

実際の点検・実行結果だけを記録する。
RED、GREEN、REFACTOR の証拠が揃ってから次の振る舞いへ進む。
最後のサイクルも同じ条件で閉じる。

## 既存コードのリファクタリング

振る舞いを変えない依頼では、既存テストで安全網を確認する。
不足していれば現在の契約を記録する特性テストを追加する。
特性テストが最初から成功することは正常であり、人工的な RED は作らない。
小さな構造変更ごとに再検証し、REFACTOR の点検と判断を残す。
振る舞いの変更を含む場合は、その部分を別の RED から始める。

## 中断と完了

中断時は現在の工程と次の作業を記録する。
GREEN 直後に中断したら、再開時は REFACTOR から続ける。
点検を飛ばしたことに気づいたら、次の実装を止めて未点検の差分を確認する。
後から点検した場合は、その事実を記録し、実施時点を偽らない。

完了前に全サイクルの点検記録と、変更全体の関連テストを確認する。
実行できない検証や未完了の点検があれば、その範囲と理由を報告する。
完了確認には [verifying-changes](../verifying-changes/SKILL.md) を使う。
