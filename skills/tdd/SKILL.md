# Test-Driven Development

## Philosophy

### コア原則

テストは実装の詳細ではなく、公開インターフェースを通じて振る舞いを検証すべきである。
コードが大きく変更されても、テストはその影響を受けるべきではない。

### 良いテストとは

良いテストは、公開インターフェース単位で振る舞いを確認する。

内部関数を直接テストするのではなく、
ユーザーや他モジュールから見える API を通して確認する。

また、良いテストは仕様書のように読める。

例えば以下の通りである。

- 「有効なメールアドレスでユーザーがログインできる」

というテスト名であれば、システムにどのような機能があるのかが明確にわかる。

こうしたテストは内部構造に関心を持たないため、リファクタリング後も壊れにくい。

### 悪いテストとは

悪いテストとは、実装に密結合なテストである。

- 内部で使用している依存先をモックする
- private メソッドをテストする
- インターフェースを経由せず、外部手段で検証する (例: API を使わずに DB を直接見る)

> リファクタリングしただけで、振る舞いは変わっていないのにテストが壊れる

このような状態は危険なため、設計を見直す必要がある。
もし、内部の関数名を変更しただけでテストが失敗するなら、そのテストは振る舞いではなく実装をテストしてしまっている。

---

## Anti-Pattern: Horizontal Slices

**すべてのテストを書いてから、まとめて実装を書くのは禁止。**

これは「horizontal slicing」であり、RED を「全テストを書くフェーズ」、GREEN を「全実装を書くフェーズ」と誤解している。

これは **ゴミみたいなテスト** を生む。

- テストが実際の振る舞いではなく「想像上の振る舞い」を検証してしまう
- データ構造や関数シグネチャなど、「形」をテストするようになる
- 振る舞いが壊れてもテストが通り、問題ない変更でテストが落ちる
- 実装を理解する前にテスト構造を固定化してしまう

---

## Correct Approach: Tracer Bullets

1テスト → 1実装 → 繰り返しのサイクルで進める。
各テストは、前のサイクルで得た知見を元に記述する。

実装直後だからこそ、何が重要な振る舞いか、何を検証すべきかを正しく理解できる。

```text
間違い（horizontal）:
  RED:   test1, test2, test3, test4, test5
  GREEN: impl1, impl2, impl3, impl4, impl5

正解（vertical）:
  RED→GREEN: test1→impl1
  RED→GREEN: test2→impl2
  RED→GREEN: test3→impl3
  ...
```

## Workflows

### 1. Planning

コードを書く前に、以下の点を確認する。

```markdown
- [] ユーザーと、必要なインターフェース変更を確認する
- [] どの振る舞いをテストするか確認する（優先順位付け）
- [] 利用側の API をシンプルにできないか検討する
- [] 副作用とロジックの境界を明確にする
- [] テスト対象の振る舞いを列挙する （実装手順ではない）
- [] 計画についてユーザー承認を得る
```

質問（確認）すべき内容の例：

> 公開インターフェースはどうあるべきか？
> どの振る舞いを最優先でテストしたいか？

---

#### すべてをテストしようとしない

本当に重要な振る舞いをユーザーと確認すること。

テスト工数は、あらゆるエッジケースではなく、重要なパスや複雑なロジックに集中させるべきだ。

---

### 2. Tracer Bullet

まず「1つのこと」を確認するテストを1つ書く。

```text
RED: 最初の振る舞いのテストを書く → 失敗
GREEN: 最小限のコードを書く → 成功
```

これが tracer bullet である。
エンドツーエンドの経路が成立していることを確認する。

---

### 3. Incremental Loop

残りの各振る舞いについて、以下の手順を繰り返す。

```text
RED:   次のテストを書く → 失敗
GREEN: 通すための最小実装を書く → 成功
```

Rules:

- 一度に1テスト
- 現在のテストを通す最小コードのみ書く
- 将来のテストを先回りしない
- テストは観測可能な振る舞いに集中する

### 4. Refactoring

全テスト通過後にリファクタリングを検討する。

- [] 重複した処理や責務を整理する
- [] 利用側から見える API を単純に保つ
  - 複雑な処理はモジュール内部へ閉じ込める
- [] 責務の分離が適切か見直す
- [] 依存方向が不自然になっていないか確認する
- [] 新しい実装によって既存設計の不自然さが見えていないか確認する
- [] リファクタごとにテストを実行して振る舞いが壊れていないことを確認する

---

#### RED 状態では絶対にリファクタしない

まず GREEN にすること。

## 各サイクルのチェックリスト

```markdown
- [] テストは実装ではなく振る舞いを説明しているか
- [] テストは公開インターフェースのみを使用しているか
- [] 実装詳細に依存したテストになっていないか
- [] コードはこのテストに対する最小実装か
- [] 将来必要になりそうという理由だけでコードを書いていないか
```
