# Planning Changes

## 計画の単位

設計と対象コードを読み、利用者が確認できる振る舞いでタスクを分ける。
「全テストを書く」「全実装を書く」という分割はしない。
各タスクは、それ単独で検証できる結果を持つ。

各タスクに次を記載する。

- 期待する振る舞いと完了条件。
- 変更候補のファイルと既存の利用箇所。
- 前提、依存するタスク、互換性への影響。
- 最初に確認するテストと、実行する検証コマンド。
- RED、GREEN、REFACTOR 点検、点検後の検証の完了欄。

実装コードや全テストを計画段階で書き切らない。
次のテストと設計の詳細は、前の TDD サイクルで得た知見から決める。
タスクが大きすぎる場合は、最初の経路が動く小さな振る舞いへ分ける。

## 計画の使い方

短い計画は会話に残し、引き継ぎが必要なら既存の保存規約に従う。
規約がなければ docs/plans/ を使う。
仕様上の重要な未決事項がなければ、承認を繰り返し求めず実行する。

実装では [tdd](../tdd/SKILL.md) を使う。
REFACTOR 点検が未記録のタスクは、GREEN でも未完了とする。
全タスク終了後は [verifying-changes](../verifying-changes/SKILL.md) で
要求と結果を照合する。
