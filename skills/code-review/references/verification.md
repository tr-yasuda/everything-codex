# Verification

各指摘は、最終レポートへ残す前に必ず検証する。

検証では、指摘が成立する根拠だけでなく、成立しない可能性も確認する。

---

## 確定

以下をすべて確認できる場合は `確定` とする。

- 発生条件を特定できる
- 問題へ到達する処理経路を特定できる
- 誤った挙動を具体的に説明できる
- 影響範囲を説明できる
- 問題を防ぐ別の guard、validation、型、制約が存在しない
- 問題となる経路が実際に到達可能である

`確定` とする場合は、具体的な発生シナリオを説明できなければならない。

---

## 高確度

問題の仕組みはコード上で成立しているが、発生条件の一部を静的に確定できない場合は `高確度` とする。

例は次のとおり。

- 実行タイミングに依存する
- 本番環境の設定に依存する
- 外部サービスの挙動に依存する
- 実行時のデータに依存する
- retry や scheduling の順序に依存する

`高確度` とする場合は以下を明示する。

- 未確定の条件
- その条件が現実的に発生し得る理由
- 何を確認すれば `確定` にできるか

---

## 未確認

以下の場合は `未確認` とする。

- 発生条件を特定できない
- 問題となる経路が実際に到達可能か確認できない
- 誤った挙動を具体化できない
- 影響を説明できない
- 指摘を成立させるために複数の仮定が必要になる

`未確認` は最終レポートに含めない。

---

## 否定

以下を確認できる場合は `否定` とする。

- 呼び出し元で必要な条件が保証されている
- 別の場所に guard / validation が存在する
- 型や入力定義によって不正な状態を表現できない
- transaction、lock、unique constraint などで防がれている
- API の仕様上、その入力や状態が成立しない
- 既存コードがすでに問題を処理している
- 指摘していた経路に実際には到達できない

`否定` は最終レポートに含めない。

---

## 反証の確認

各指摘について、以下を必ず確認する。

- 呼び出し元、validation、型、制約などによって問題がすでに防がれていないか
- transaction、lock、unique constraint などによって実行時に問題が成立しない構造になっていないか
- 指摘している経路が実際に到達可能で、既存テストや API の仕様と矛盾していないか

これらを確認したうえで反証できない指摘だけを `確定` または `高確度` とする。

---

## 判定ルール

確度と重要度は分けて考える。

- 確度は、その指摘が本当に成立するかどうか
- 重要度は、実際に起きたときの影響の大きさ

確信が持てないからといって、重要度まで下げない。
