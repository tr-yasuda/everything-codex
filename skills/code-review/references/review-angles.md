# Review Angles

reviewer は自分の担当範囲について、以下の方法で変更を掘り下げる。

---

## 変更行を読む

追加・削除・変更された処理について、何が変わったかを確認する。

特に以下を見る。

- 条件分岐
- validation
- guard
- error handling
- 戻り値
- 副作用
- DB / network access
- resource の取得・解放

---

## 呼び出し元・呼び出し先を追う

変更された処理だけで判断せず、必要な範囲で呼び出し元と呼び出し先を追う。

```text
呼び出し元 → 変更箇所 → 呼び出し先
```

以下を確認する。

- 呼び出し元の前提が壊れていないか
- 呼び出し先の仕様と食い違っていないか
- 戻り値や error の変更が利用側まで正しく伝わっているか
- 公開 API の変更を利用側が正しく扱えているか

---

## 削除された処理の意味を確認する

削除・置換された以下の処理が、何を守っていたか確認する。

- guard
- validation
- authorization
- error handling
- retry
- timeout
- cleanup
- assertion
- test

削除前に守られていた条件が、新しい実装でも維持されているか確認する。

---

## 状態遷移を追う

状態を持つ処理では、変更前後の状態遷移を確認する。

以下を見る。

- どの状態から開始するか
- どの状態へ遷移できるか
- 許可されていない遷移が増えていないか
- 終了状態から処理を再実行できてしまわないか
- retry や重複実行で状態が壊れないか

---

## 境界条件を確認する

入力や件数に境界がある処理では、少なくとも以下を確認する。

- 空
- 未指定
- 最小値
- 最大値
- 過大な入力
- 削除済み・失効済み
- 不正な値

通常ケースだけで判断しない。

---

## 認可の流れを追う

resource へアクセスする処理では、以下の流れを追う。

```text
利用者
↓
resource ID
↓
取得
↓
認可
↓
参照 / 更新 / 削除
```

利用者が指定した ID だけで resource を取得・更新できる構造になっていないか確認する。

---

## 並行処理を時系列で考える

同時実行があり得る処理では、複数の処理を時系列に並べる。

例は次のとおり。

```text
A: 状態を読む
B: 状態を読む
A: 更新する
B: 更新する
```

そのうえで、transaction、lock、unique constraint、冪等性がどこで効くか確認する。

---

## retry を追う

retry がある処理では、同じ操作が複数回実行された場合を確認する。

以下を見る。

- 副作用が重複しないか
- 同じ request ID / idempotency key を維持しているか
- retry 可能な error と retry すべきでない error を区別しているか
- retry 後に状態や順序が壊れないか

---

## エラー時の処理を追う

正常系だけでなく、途中で失敗した場合の経路を確認する。

以下を見る。

- どこで error が発生するか
- cleanup を実行しているか
- 一部だけ更新された状態が残らないか
- 処理結果に対応した error を呼び出し元へ返すか
- log や metrics に必要な情報が残るか

---

## resource の上限を確認する

増え続ける可能性があるものに上限があるか確認する。

例は次のとおり。

- collection
- queue
- task
- worker
- connection
- stream
- request body
- query result

入力や負荷に比例して無制限に増える構造になっていないか確認する。
