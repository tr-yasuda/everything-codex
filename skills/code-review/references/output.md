# Output

最終レポートは、読み手が短時間で判断できることを優先する。

レビュー中に確認した詳細をすべて並べず、意思決定に必要な情報だけを残す。

---

## 基本構成

```markdown
# Code Review

## Summary

- 今すぐ直す: 1件
- マージ前に確認: 2件
- 軽微: 0件

主なリスクは、認可漏れと retry 時の重複処理です。

## Findings

### [今すぐ直す] 他 tenant の resource を取得できる

**確度:** 確定

**対象:** `src/resource.ts:42`

tenant 条件なしで resource を取得しているため、別 tenant の ID を指定すると他 tenant のデータを参照できます。

**影響:** tenant 間のデータ漏洩につながります。

**推奨対応:** repository query に tenant 条件を追加してください。

---

### [マージ前に確認] retry 時に副作用が重複する

**確度:** 高確度

**対象:** `src/payment.ts:88`

timeout 後の retry で同じ処理が再実行され、二重作成される可能性があります。

**影響:** 同じ副作用が複数回発生します。

**推奨対応:** retry 時も同じ idempotency key を維持してください。
```

---

## Summary

最初に、レビュー結果を次の3つに分けて件数を示す。

- 今すぐ直す: マージ前に修正すべき問題
- マージ前に確認: そのままマージしてよいか判断が必要な問題
- 軽微: マージを止めるほどではないが、明確な改善価値がある問題

その下に、主なリスクを1〜2文でまとめる。

詳細なレビュー手順や reviewer ごとの結果は書かない。

---

## Findings

指摘は以下の順番で並べる。

1. 今すぐ直す
2. マージ前に確認
3. 軽微

各指摘には以下を含める。

- 対応区分
- 確度
- 対象箇所
- 問題
- 影響
- 推奨対応

発生条件、処理経路、根拠、回帰テストは、判断に必要な場合だけ補足する。

同じ根本原因、または同じ修正で解決できる指摘は1件にまとめる。

1件の指摘を長くしすぎない。

---

## 対応区分

### 今すぐ直す

そのままマージすると、重大な不具合、セキュリティ問題、データ破損、本番障害につながる問題。

### マージ前に確認

成立する可能性が高い問題のうち、マージ前に修正または判断すべきもの。

### 軽微

影響は限定的だが、明確な不具合や保守性の問題があるもの。

style preference や好みだけの指摘は含めない。

---

## 指摘がない場合

問題を作らない。

```markdown
# Code Review

## Summary

- 今すぐ直す: 0件
- マージ前に確認: 0件
- 軽微: 0件

重大な問題は見つかりませんでした。
```

---

## 出力ルール

- 同じ内容を Summary と Findings で繰り返さない
- reviewer ごとの中間結果を出さない
- `未確認` または `否定` になった指摘は出さない
- 根拠の弱い推測を出さない
- style preference や好みだけの指摘を出さない
- 長い背景説明より、問題・影響・対応を優先する
- 指摘が多い場合でも、上から読むだけで優先順位が分かる構成にする
- 指摘がない場合は無理に問題を作らない
