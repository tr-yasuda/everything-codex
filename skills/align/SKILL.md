# Align

## 目的

実装前に、エージェントとユーザーが同じ困りごと・同じゴール・同じ制約を、
同じ意味で持っている状態を作る。

認識のズレは、作る前なら少ない手間で直せる。
作り始めてから気づくと、作り直しになる。

この skill の成果は、仕様書ではない。
ユーザーが、なぜこの変更をするのかを理解している。
何が変わり、何が変わらないのか、何を手放すのかも理解している。
エージェントも同じ内容を理解している状態そのものとする。

どちらか一方の理解を正としない。
事実と意図を突き合わせて、同じ認識を作る。

固定の見出しに当てはめない。
合意した内容は、必要な項目だけを短く会話に残す。

## Workflow

1. 依頼と、関連する既存の仕様・コードを読む
2. エージェントの理解を短く言い返し、ユーザーにズレを訂正してもらう
3. 依頼の通りに進めても、困りごとが解決するかを確かめる
4. 技術的な判断を共有し、ユーザーの認識と合っているか確かめる
5. ユーザーの価値観でしか決められない点だけを聞く
6. 合意した理解を短く残す

### 1. 依頼と現状を読む

依頼文と、関連する既存の仕様・コードを読む。

次の 3 つを分けて持つ。

- ユーザーが明示したこと
- エージェントが読み取ったこと
- まだ確かめていないこと

コードや仕様から分かることを、ユーザーに聞かない。

### 2. 理解を言い返す

エージェントの理解を、数文でユーザーに返す。
ユーザーにゼロから説明させず、正誤を訂正できる形にする。

依頼が明確なら、確認は短くする。
曖昧なら、理解を言い返して掘り下げる。

次の内容を含める。

- 困りごと
- ゴール
- 守るべき制約
- 何が変わり、何が変わらないか

ユーザーの言葉を使い、内部の用語を使わない。
確かめていないことが結論に影響するなら、その旨も書く。

例を示す。

```text
私は、完了したタスクが増えて一覧が見づらい、という困りごとだと理解しました。
今回はタスクを削除せず、全件と未完了を切り替える方向で考えています。
この理解で合っていますか。
```

### 3. ズレを扱う

依頼の通りに進めても困りごとが解決しないと分かったら、そのまま進めない。
何が解決しないのか、なぜかを短く伝え、別の進め方を示す。

ユーザーが理解を訂正したら、訂正を反映した理解を短く言い返す。
訂正前の理解で進めない。

### 4. 技術的な判断

既存の仕様・コードから決められる技術的な事項は、エージェントが決める。
決めた内容と理由を共有し、ユーザーの認識と合っているか確かめる。

特に、次のどれかが変わる判断は、理由まで伝える。

- 利用者から見える振る舞い
- 公開インターフェース
- 互換性
- データの扱い
- ユーザーが手放すもの

技術的な判断を、ユーザーに選択肢として押し付けない。
判断がまだ決められない場合は、何が分かれば決められるかを伝える。

### 5. ユーザーに聞くこと

ユーザーに聞くのは、ユーザーの価値観や優先順位で結果が変わる点だけにする。

- 利用者から見える振る舞い
- 公開インターフェース
- 互換性
- データの扱い
- 何を優先し、何を手放すか

質問は、答えによってエージェントの理解が変わるものに絞る。
関連する質問は一度にまとめてよいが、ユーザーが答えやすい単位に分ける。
すでに合意した内容を、もう一度聞かない。

選択肢を示すのは、ユーザーが選ぶことで結果が変わり、
エージェントが代わりに決められないときだけにする。
選択肢を示す場合も、推奨を先に 1 つ示し、各選択肢で何が変わるかを 1 行で書く。

ユーザーに要約や言い直しを求めない。
理解度を試す質問をしない。

### 6. 合意した理解を残す

認識が合ったら、合意した内容を会話の中で短くまとめる。

次の内容を含める。

- 困りごと
- ゴール
- 変えること
- 変えないこと
- 守るべき制約
- まだ決まっていないこと

固定の見出しは使わない。
必要な項目だけを、数行で書く。
ファイルには保存しない。

仕様書が必要なら `write-spec` に引き継ぐ。

## 実装への引き継ぎ

認識が合ったあと、ユーザーから実装を依頼された場合は、次の順で進める。

1. `what-breaks` で、変更箇所以外で壊れ得る場所を確かめる
2. `tdd` で、RED → GREEN → REFACTOR のサイクルごとに実装する
3. `prove-it` で、完了を報告する前に差分を点検し、実際の動作を確かめる

各 skill の手順と、使えない場合の扱いは、それぞれの `SKILL.md` に従う。

## やり取りの書き方

- 1 回の発言は、ユーザーが判断するのに必要な内容だけにする
- 長い前置き、読んだ内容の要約、作業ログを書かない
- 同じ説明を繰り返さない
- 専門用語や内部の事情を前提にしない
- ユーザーが読む量を増やす確認を続けない

## Rules

- 目的は仕様書を埋めることではなく、エージェントとユーザーが同じ意味で理解していること
- エージェントの理解を先に言い返し、ユーザーにゼロから説明させない
- ユーザーの訂正を次の理解に反映し、訂正後の理解を短く確認する
- 技術的に決められることはエージェントが決め、判断と理由を共有して認識を確かめる
- ユーザーに選択肢を押し付けず、価値観や優先順位が関わる点だけを聞く
- 確認は、認識が変わり得る点だけに絞る
- 選択肢を示すのは、ユーザーが選ぶことで結果が変わり、エージェントが代わりに決められないときだけにする
- ユーザーに要約や言い直しを求めず、理解度を試す質問をしない
- 固定の見出しやテンプレを使わない
- 合意した内容は会話に短く残し、ファイルには保存しない
- 仕様書は `write-spec` に引き継ぐ
- 実装手順や変更ファイル単位の計画には踏み込まない
- 合意後の実装では `what-breaks` → `tdd` → `prove-it` を使う
