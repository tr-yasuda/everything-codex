# Output

最終レポートは、読み手がその場で意思決定できることだけを残す。
テンプレの項目を埋めない。修正済みの内容を長く説明しない。

---

## 構成

先頭に、ユーザーが決める事項を置く。該当する事項がない場合は、その旨を1行で書く。
その後に、直したことを対象と変更内容が分かる1行で並べる。
確認できなかった範囲がある場合だけ、最後に書く。

見出しは読みやすさのために使う。空の見出しや、埋めるための項目を作らない。

例を示す。

```markdown
# Code Review

## 判断が必要

retry 時の重複をどう扱うか（`src/payment.ts:88`）。

- 現在: timeout 後の retry で、同じ注文が二重に作成される。
- 同じ注文として扱う: 重複作成は防げるが、再送された決済の意図は拾えない。
- 新しい注文として扱う: 意図は拾えるが、二重作成を防ぐには別のキーが必要。
- 推奨: 同じ注文として扱い、注文 ID を retry キーにする。
- 未回答: 推奨で進める。

## 直したこと

- `src/resource.ts:42`: resource の取得条件に tenantId を追加。
- `src/format.ts:12`: 空文字をそのまま返すよう修正。

## 確認できなかった範囲

- 独立した再確認は subagent を起動できず未実施。8観点は親が代替点検した。
```

---

## 判断が必要な事項

次の内容が揃っていない判断事項は出さない。

- 何を決めるのか
- 現在の挙動
- 選択肢ごとの結果
- 推奨
- 未回答時の扱い

コードを読まなくても決められる言葉で書く。必要なら対象箇所を添える。
選択肢は、結果が実質的に変わるものだけに絞る。好みだけの選択肢を並べない。

判断が必要なのは、直し方が意図・優先順位・トレードオフで変わる場合だけ。
不確かなだけの場合は、判断事項にせず追加で調べる。調べても成立しないなら出さない。
材料が揃わない場合は、判断事項として出さず、追加で調べるか、決めて直す。

---

## 直したこと

- 対象箇所と変更内容を1行で書く。
- 問題の説明、影響、根拠は、判断に必要でない限り書かない。
- 複数ファイルにまたがる同じ修正は、まとめて1行にしてよい。
- 修正の意図が自明でない場合だけ、1文補足する。

---

## 確認できなかった範囲

- 8観点の確認や、必要と判断した独立再確認を実施できなかった場合だけ書く。
- 確認できなかった範囲を、問題なしの範囲に含めない。
- 代替した点検がある場合は、その範囲と理由を書く。

---

## 指摘がない場合

問題を作らない。

```markdown
# Code Review

判断が必要な点はありません。修正もありません。
```

修正だけした場合は、判断が必要ない旨を1行で書いた後に、直したことを並べる。
確認できなかった範囲がある場合は、その旨を添える。

---

## 出力ルール

- 重要度の区分（今すぐ直す、マージ前に確認、軽微）を作らない。
  修正したか、判断が必要か、確認できなかったかで分ける。
- 同じ内容を要約と本文で繰り返さない。
- reviewer ごとの中間結果を出さない。
- `未確認` または `否定` になった指摘を出さない。
- 根拠の弱い推測を出さない。
- style preference や好みだけの指摘を出さない。
- 長い背景説明より、判断に必要な材料と、実施した修正を優先する。
- 読み手が内容を聞き直さなくても決められる書き方にする。
- 読み手に感想や意見を聞き返さない。判断に必要な材料、推奨、未回答時の扱いを示す。
- 修正の詳細を読ませる必要がある場合は、対象箇所と変更内容だけを示す。

---

## 根拠の書き方

- 判断事項と修正内容には、コード、テスト、仕様で確かめた事実を書く。
- 別の指摘に付け替えても通じる文は書かない。
  「保守性が下がります」は、どの指摘にも付けられる。
- 確認できなかった範囲は、推測で埋めず、その旨を書く。
