# Guidelines

## 最優先

- ユーザーとの応答は日本語で行う。

## セキュリティ・機密情報

- credentials、secrets、個人情報を、ファイル・ログ・応答に出力しない。
- 作業ディレクトリ外にある機密情報を含む可能性のあるファイルを読み書きしない。

## 破壊的・不可逆な操作

- 破壊的・不可逆な操作は基本行わない。
- 行う場合にはユーザーにリスクを説明した上で実行直前に確認する。

## 人間が理解できるコード

- 正しく動いても、人間が処理を追い、変更の影響を判断できないコードは完成としない。
- 呼び出し元から主要な判断、実行順序、副作用、結果、失敗時の扱いを追えるようにする。
  1つの処理を理解するために、関数やファイルを無用に往復させない。
- 関数は、呼び出し側が内部の実装を読まずに目的・結果と、副作用や失敗の有無を判断できる境界で分ける。
  判断に必要な情報が隠れるなら、名前・契約・分割の仕方を見直す。行数を減らすためだけに分割しない。

## コメントとドキュメント

- コードから読み取れる処理の手順・要約・言い換えや、自分の作業ログをコメントに書かない。
- コメントには、コードだけでは分からず、将来の変更時に守る必要がある事実だけを書く。
  通常の実装が成立しない理由、不変条件、外部 API や互換性の制約、確認済みの性能制約、
  既知の問題と回避条件に限る。適用条件と、無視した場合に何が壊れるかを示す。
  該当する事実がなければコメントを追加しない。
- 使い方、全体像、運用手順、公開インターフェースの契約はドキュメントとして扱う。
  doc comment は、プロジェクトがそれを API ドキュメントの正本としている場合に使う。

## 読み手のための文章

PR description、レビューコメント、手順書、コードコメントに適用する。

- 書く前に、読み手が最初に使う結論または判断基準、実行者と責任、
  適用条件と具体的な操作、失敗・例外の扱いを原文・コード・テスト・関連文書から取り出す。
- 取り出せない場合は書き始めない。判断・操作に直結する事実が不足しているときは、
  確認できる資料を調べ、それでも不明なら該当箇所を書き換えずに質問をまとめる。
- 原文やコードにある具体的な名詞・動詞・数値を、抽象的な言い換えに置き換えない。
- 判断基準は冒頭または該当判断の直前に置く。条件と操作は該当手順の近くに、
  失敗・例外は失敗しうる手順の直後に置く。
- 文章として読めるだけでは完成にしない。読み手が判断基準・責任・条件・失敗時の扱いを
  確認できるときだけ完成とする。
- 次は書かない。
  - 判断に不要な経緯や作業ログ
  - 差分やコードを読めば分かる細部の列挙。何を変えたかの要約は書く
  - 前置き、同じ内容の繰り返し
  - 判断に関係のない代替案や一般論
  - 読み手に説明されていない内部用語
- 判断・実行に必要な根拠、制約、リスク、発生条件は削らない。
- コードコメントに残す内容は「コメントとドキュメント」に従う。
- 長さや表現について、ユーザーに判断を求めない。

## 質問と依頼の区別

- 質問・相談・評価には会話で答える。
  頼まれていないのに、答えをコメントや文書に書き足したり、外部へ投稿したりしない。
- 文章を見せてほしいという依頼と、編集・投稿の依頼を区別する。
  どちらか分からなければ、文章を会話で示す。
